<Step id="mean" title="An average can hide the slow users">

Imagine 99 requests take 10 ms each and one takes 1,010 ms. The mean is 20 ms, yet one user waited over a second. Averages answer questions about total work and Little's law; they do not describe the experience of the slowest users.

A percentile describes a point in an ordered distribution. A p99 of 200 ms says about 99% of measured observations are at or below that value under the chosen convention. It does not promise that every user gets 200 ms or that the worst request takes only a little longer.

]} />

</Step>

<Step id="rank" title="Calculate the rank before reading the value">

We use **nearest rank = ceil(p × N)** with one-based indexing. For 1,000 sorted samples, p99 uses rank 990. Read the latency value at that rank; the rank itself is not a time measurement.

With very few samples, high percentiles collapse toward the maximum and vary sharply between windows. A p99 from ten requests is weak evidence for a service handling millions. State the sample size, observation interval, included statuses and quantile convention when comparing results.

<Step id="aggregation" title="Do not average machine percentiles">

Suppose one server receives 100 requests and another receives 100,000. Their local p99 values do not contain enough information to reconstruct the fleet p99. Even weighting those two values by request count generally fails because a quantile is not a mean.

Aggregate compatible histogram bucket counts, or use a mergeable distribution sketch with a known error bound. Then calculate the percentile for the combined observations. Check bucket resolution near your SLO; a coarse bucket spanning 100 ms to 1,000 ms gives a weak estimate of a 200 ms objective.

<Step id="fanout" title="A rare branch delay becomes common in fan-out">

A search request queries 100 shards and needs every result. If each independent shard has a 1% chance of exceeding a threshold, the chance all are fast is **0.99^100 ≈ 36.6%**. About **63.4%** of parents encounter at least one slow branch.

The formula is **P(any slow) = 1 − (1 − q)^n**. It gives a probability at a chosen threshold, not an exact end-to-end p99 latency. Correlated pauses, shared queues and unequal shard distributions change the result. Dean and Barroso's tail-at-scale paper motivates treating these rare delays as a system-level problem.

<Step id="correlation" title="Check the independence assumption">

If all shards share a network bottleneck, their delays may happen together. Multiplying independent probabilities then misstates the actual parent distribution. At the extreme, if every branch crosses the threshold on exactly the same requests, the parent slow probability equals the single-branch slow probability.

Real systems mix correlated and independent causes. Trace which branches slow down together and group requests by region, payload, tenant and dependency. A fleet graph can hide one badly affected tenant behind many fast small requests.

<Step id="mitigate" title="Reduce tails without causing another queue">

First remove avoidable variance: bound batch size, control admission, fix hot partitions and isolate noisy workloads. If the response can tolerate partial results, a deadline can bound waiting, but it changes the result contract and must be visible to the caller.

Hedged requests send an extra copy after a delay and use the first acceptable response. They can reduce some read tails, but extra work competes for capacity. Bound the hedge rate, avoid unsafe side effects, and cancel losers where supported. Hedging an already saturated dependency can make the tail worse.

<Step id="measurement" title="Measure the wait the user actually experienced">

A client that waits for a slow request before generating the next one can miss delays that a constant arrival stream would have encountered. Record the load model and include time spent waiting before execution when that time belongs to the user-visible boundary.

Keep both latency and availability views. A one-second timeout is a failed user request even if it produces no successful response sample. A success-only p99 may improve while more requests fail. Look at rates, sample counts and failures before celebrating a percentile change.
