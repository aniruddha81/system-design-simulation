<Step id="request-path" title="A URL becomes a request">

You enter `https://shop.example/orders/42`. The browser needs an address for the host, a connection to that address, and an authenticated encrypted channel before it sends the HTTP request. The path `/orders/42` goes to the server; a URL fragment after `#` stays in the browser.

For a cold HTTPS request over TCP, the useful order is **DNS → TCP → TLS → HTTP**. A warm browser can reuse cached DNS answers and existing connections, so a waterfall may omit several stages. A fast application cannot compensate for repeated cold setup across a distant network.

<Step id="dns" title="DNS answers have a lifetime">

The browser usually asks a recursive resolver. That resolver follows cached answers or asks the authoritative hierarchy. An A record gives an IPv4 address; AAAA gives IPv6; a CNAME points to another name. The record's **TTL** controls how long an answer may be cached.

A low TTL increases query traffic and can help future clients discover a new address sooner. It does not push an update into every browser, close existing connections, or repair a failed backend. During migration, keep both destinations serving while old answers and connections drain.

<Step id="handshake" title="Count the round trips before optimizing code">

Use a simple cold-path budget: one RTT for TCP setup, one for a full TLS 1.3 handshake, and one for the HTTP request and first response byte. Add server processing. At 60 ms RTT and 10 ms server work, that is **3 × 60 + 10 = 190 ms** before downloading the response body.

This is a teaching model, not a universal protocol stopwatch. Cached DNS is assumed. Connection reuse removes setup costs; session resumption and early data have different rules. TLS 0-RTT early data can be replayed, so accepting it requires application-level replay safety.

<Step id="tls" title="Encryption does not decide permission">

TLS protects data in transit and lets a client authenticate the server's certificate identity. It does not decide whether the signed-in user may read order 42. That authorization check belongs to the application on every protected resource.

A reverse proxy may terminate TLS and open a separate upstream connection. Draw both trust boundaries in an interview. A browser padlock says nothing about encryption between that proxy and the database, nor about whether the handler exposes another customer's record.

<Step id="versions" title="Multiplexing changes where requests wait">

HTTP/1.1 commonly uses persistent connections, but browsers usually avoid pipelining; concurrency often requires multiple connections. HTTP/2 multiplexes streams over one TCP connection. A lost TCP segment can delay delivery of later bytes for every stream sharing that connection.

HTTP/3 maps requests onto QUIC streams. Loss on one stream need not block delivery on another stream that has its data. The streams still share network capacity and congestion control, so HTTP/3 does not make loss or congestion free. Measure the workload rather than promising every request becomes faster.

<Choice id="http-loss" objective="compare-http-transports" prompt="A packet carrying one HTTP/3 response stream is lost. What advantage can QUIC offer over HTTP/2 over TCP?" options={[
  { id: "streams", text: "Other streams can deliver received data without waiting for that stream's missing bytes", correct: true, feedback: "Right. QUIC separates stream delivery; shared congestion control and connection-level limits still apply." },
  { id: "no-loss", text: "Lost bytes no longer need retransmission", feedback: "Reliable streams still recover missing data. The advantage is avoiding transport delivery blocking across independent streams." },
  { id: "udp", text: "Using UDP means there is no congestion control", feedback: "QUIC implements congestion control above UDP. UDP alone is not the complete protocol." }
]} />

</Step>

<Step id="semantics" title="A timeout does not mean nothing happened">

HTTP separates method semantics from transport. GET is intended to be safe; PUT and DELETE are idempotent in their intended effect. POST has no general idempotency guarantee. A connection can fail after a server commits a payment but before the response arrives.

For retried creates, an application can associate an idempotency key with the operation and its durable result. The same key must describe the same request. A transport retry alone cannot establish whether the original side effect happened.

<Choice id="post-timeout" objective="compare-http-transports" prompt="A payment POST times out after the server may have committed it. Which retry plan avoids creating a second payment?" options={[
  { id: "key", text: "Reuse an application idempotency key whose result is recorded durably", correct: true, feedback: "Right. The server can return the earlier result for the same operation rather than applying the effect again." },
  { id: "new", text: "Generate a new key for every retry", feedback: "A new key identifies a new operation, so it defeats deduplication of the original payment." },
  { id: "tcp", text: "Assume TCP failure proves the server rolled back", feedback: "The response can be lost after commit. A failed connection does not reveal transaction outcome." }
]} />

</Step>

<Step id="updates" title="Choose how updates reach the browser">

Polling is simple when seconds of delay are acceptable; long-polling holds a request until an update or timeout. **SSE** sends a one-way server event stream over HTTP and includes reconnection support. **WebSockets** support messages in both directions after establishing a persistent connection.

For a dashboard that receives updates but sends occasional commands by ordinary HTTP, SSE can be enough. For an interactive game with frequent bidirectional messages, WebSockets are a better fit. Either choice needs bounded buffers, authentication renewal and a reconnect strategy; reconnecting is not proof that missed events were replayed.

<Choice id="dashboard-updates" objective="choose-update-transport" prompt="A status dashboard needs server-to-browser updates every second. User commands are rare HTTP requests. Which is a straightforward fit?" options={[
  { id: "sse", text: "SSE with event IDs and a defined replay policy", correct: true, feedback: "Right. The main flow is one-way; IDs plus server retention can support recovery after reconnect." },

  { id: "required", text: "WebSockets are mandatory for any server update", feedback: "WebSockets are useful for bidirectional traffic, but HTTP streaming and polling also deliver server updates." }
]} />
