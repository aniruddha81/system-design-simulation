<Step id="request-path" title="A URL becomes a request">

Cold HTTPS over TCP: **DNS, then TCP, then TLS, then HTTP**. A warm browser skips stages.

<Step id="dns" title="DNS answers have a lifetime">

The **TTL** says how long an answer may be cached. Changing it does not reach cached answers or open connections.

<Timeline title="DNS change during an outage" events={[
  { at: "t0", label: "Point name at new IP", tone: "info" },
  { at: "t0 + TTL", label: "Cached answers expire", tone: "warn" },
  { at: "Later", label: "Old connections drain", tone: "ok" }
]} caption="Keep both destinations serving while old answers drain." />

<Choice id="dns-failover" objective="trace-web-request" prompt="You change a DNS answer during an outage. Why do some users still connect to the old IP?" options={[
  { id: "cached", text: "They have an unexpired cached answer or an existing connection", correct: true, feedback: "Right. DNS updates affect future resolutions; cached answers and open connections can outlive the change." },
  { id: "path", text: "DNS cached the HTTP path /orders/42", feedback: "DNS resolves the host name. It does not route individual HTTP paths." },
  { id: "tls", text: "TLS always pins a domain to one IP forever", feedback: "TLS authenticates identities and negotiates keys; it does not permanently bind the name to an IP." }
]} />

</Step>

<Step id="handshake" title="Count the round trips before optimizing code">

Cold path: 1 RTT TCP + 1 RTT TLS 1.3 + 1 RTT HTTP + server work. TLS 0-RTT data can be replayed.

<Bars title="60 ms RTT, 10 ms server work" items={[

  { label: "TLS 1.3 handshake", value: 60, unit: "ms", tone: "info" },
  { label: "HTTP request", value: 60, unit: "ms", tone: "info" },
  { label: "Server work", value: 10, unit: "ms", tone: "warn" }
]} caption="Total 3 × 60 + 10 = 190 ms. A reused connection drops the first two." />

<Step id="tls" title="Encryption does not decide permission">

TLS proves who the server is and encrypts the wire. It does not decide whether this user may read order 42.

<Flow title="Two trust boundaries" height={150} nodes={[

]} edges={[{ from: "b", to: "p", label: "TLS" }, { from: "p", to: "a", label: "own connection" }]} caption="The padlock says nothing about authorization." />

<Choice id="tls-authorization" objective="trace-web-request" prompt="HTTPS is working, but changing /orders/42 to /orders/43 reveals another customer's order. What is missing?" options={[
  { id: "authorization", text: "A server-side check that the caller may access that order", correct: true, feedback: "Right. Secure transport protects the request in flight; the application must authorize access to the requested object." },
  { id: "dns", text: "A shorter DNS TTL", feedback: "DNS cache lifetime cannot establish ownership of an order." },
  { id: "http3", text: "An upgrade to HTTP/3", feedback: "Changing transport cannot fix a missing resource authorization check." }
]} />

</Step>

  { id: "streams", text: "Other streams can deliver received data without waiting for that stream's missing bytes", correct: true, feedback: "Right. QUIC separates stream delivery; shared congestion control and connection-level limits still apply." },
  { id: "no-loss", text: "Lost bytes no longer need retransmission", feedback: "Reliable streams still recover missing data. The advantage is avoiding transport delivery blocking across independent streams." },

]} />

<Step id="semantics" title="A timeout does not mean nothing happened">

A timeout does not mean nothing happened. GET is safe; PUT and DELETE are idempotent; POST is not.

<Sequence title="Payment POST with lost response" actors={["Client", "Server"]} messages={[
  { from: "Client", to: "Server", label: "POST /pay, key K" },
  { from: "Server", to: "Client", label: "committed, 200", lost: true },
  { from: "Client", to: "Server", label: "retry, same key K", tone: "info" },
  { from: "Server", to: "Client", label: "recorded result", tone: "ok" }
]} caption="Same key means same operation. A new key would charge twice." />

<Choice id="post-timeout" objective="compare-http-transports" prompt="A payment POST times out after the server may have committed it. Which retry plan avoids creating a second payment?" options={[
  { id: "key", text: "Reuse an application idempotency key whose result is recorded durably", correct: true, feedback: "Right. The server can return the earlier result for the same operation rather than applying the effect again." },
  { id: "new", text: "Generate a new key for every retry", feedback: "A new key identifies a new operation, so it defeats deduplication of the original payment." },
  { id: "tcp", text: "Assume TCP failure proves the server rolled back", feedback: "The response can be lost after commit. A failed connection does not reveal transaction outcome." }
]} />

</Step>
