<Step id="rates" title="Rate is different from time">

Latency asks how long one request takes. **Throughput** asks how many requests finish per unit time. Concurrency counts requests present at once. A service can have high throughput and high latency if many requests run or wait concurrently.

Distinguish offered load from completions. A load generator may send 2,000 requests/s while the service successfully completes 1,200/s, rejects 300/s and accumulates the rest. Label success, error and drop rates separately. Reporting only the send rate makes an overloaded service look faster than it is.

]} />

</Step>

<Step id="inflight" title="Use Little's law with matching units">

For a stable system, **L = λW**: average requests in the system equal average throughput times average time in the system. Include both queued and active requests if W includes both waiting and processing.

At 2,000 requests/s and 50 ms mean response time, average concurrency is **2,000 × 0.050 = 100 requests**. That does not mean 100 CPU cores. Requests can be waiting for I/O or a connection. Little's law is accounting, not a CPU sizing formula.

<Step id="boundary" title="Draw the system boundary first">

You can apply the law to a whole service, a database pool or just one queue, but the terms must describe the same boundary. If you count only active database queries, use query service time. If you count requests waiting for a pool slot too, include that wait in W.

Use an appropriate observation interval. A snapshot of 100 requests at one instant is not automatically the long-run average L. A sudden backlog spike also makes a short measurement window misleading: work arriving in one window may complete in another.

<Step id="capacity" title="Estimate worker capacity, then leave room">

One worker taking a constant 25 ms per job can finish at most 40 jobs/s. Eight independent workers can theoretically finish **320 jobs/s**. This ceiling assumes there is no shared database, CPU, lock or link bottleneck.

Sizing at the ceiling leaves no room for burstiness or slow jobs. A pool that is adequate at the mean may queue badly when service times vary. Benchmark the actual request mix and choose headroom for your latency goal; there is no universal utilization target that works for every workload.

<Step id="unstable" title="A queue cannot manufacture capacity">

An arrival rate of 500 jobs/s and completion capacity of 400/s adds 100 jobs to the backlog every second while those rates persist. A bigger queue delays rejection but does not make the system stable. Memory eventually fills or requests wait past their useful deadlines.

Use a bounded queue to absorb a finite burst, then drain it with spare capacity. For sustained overload, reduce work, increase the constrained resource, or reject excess arrivals. Track queue age as well as length: 1,000 jobs may be milliseconds or hours of waiting depending on throughput.

  { id: "retry", text: "Retry rejected work immediately without a limit", feedback: "Immediate retries raise offered load during overload and can worsen the backlog." }
]} />

</Step>

<Step id="closed-loop" title="Do not let the load test hide the queue">

A fixed-concurrency client sends a replacement only after an earlier request finishes. When the service slows, this client sends fewer requests per second. That can be useful for modeling users, but it can also hide overload from an external arrival stream that would keep sending.

A constant-rate arrival test asks a different question: what happens when demand does not politely pause? Use both models deliberately. Record offered load, completions and timeouts alongside latency so a lower send rate is not mistaken for recovery.

<Step id="scale" title="Scaling one tier can expose the next bottleneck">

Adding stateless workers helps only until a shared resource saturates. If every request holds a database connection for 20 ms and the pool has ten usable slots, the pool bounds that path near 500 requests/s under the simplified constant-time model.

Watch where time is spent before scaling. More web workers cannot increase a fixed link's bandwidth or remove a hot-row lock. After any intervention, repeat the same workload and compare completions, queue age and error rate as well as latency.
