<Step id="rates" title="Rate is different from time">

Latency is how long one request takes. **Throughput** is completions per second. Label offered, completed, rejected and queued separately.

]} caption="Reporting only the send rate hides overload." />

  { id: "measure", text: "Offered load is 2,000/s; successful throughput is 1,200/s", correct: true, feedback: "Right. You still need error, rejection and queue measurements to account for the remaining arrivals." },

  { id: "latency", text: "Mean latency must be 800 ms", feedback: "Subtracting rates produces another rate, not a duration. Latency requires timing or a valid Little's-law calculation." }
]} />

<Step id="inflight" title="Use Little's law with matching units">

**L = λW** for a stable system. Include queue wait in W if you include queued requests in L. It is accounting, not CPU sizing.

<Step id="boundary" title="Draw the system boundary first">

L and W must describe the same boundary. Use a long enough window; one snapshot is not the average.

<Flow title="Pool boundary" height={150} nodes={[

  { id: "a", label: "Active queries", kind: "database", x: 100, y: 50, note: "40 active" }
]} edges={[{ from: "q", to: "a" }]} caption="W = 100 ms from queue entry to completion, so L = 40 + 60 = 100." />

<Choice id="law-boundary" objective="apply-littles-law" prompt="A pool reports 40 active queries plus 60 waiting requests on average. Mean time from entering the pool queue to completion is 100 ms. Which L matches that W?" options={[
  { id: "whole", text: "100 requests, counting waiting and active work", correct: true, feedback: "Right. The response-time boundary starts before pool waiting, so both groups belong in L." },
  { id: "active", text: "40 requests, counting only active queries", feedback: "That would require a service-time measurement excluding the queue wait." },

]} />

</Step>

<Step id="capacity" title="Estimate worker capacity, then leave room">

One worker at 25 ms/job: 40 jobs/s. Eight workers: at most 320 jobs/s, if nothing shared saturates. Leave headroom; there is no universal target.

<Step id="unstable" title="A queue cannot manufacture capacity">

Arrivals 500/s, capacity 400/s: backlog grows by 100 jobs every second. A bigger queue only delays the failure. Track queue age, not just length.

<Bars title="Backlog after t seconds" items={[
  { label: "10 s", value: 1000, unit: "jobs", tone: "warn" },
  { label: "60 s", value: 6000, unit: "jobs", tone: "bad" },
  { label: "600 s", value: 60000, unit: "jobs", tone: "bad" }
]} caption="Admit only the sustainable rate, add capacity, or shed load." />

<Choice id="unbounded-queue" objective="identify-unstable-queue" prompt="Arrivals stay at 500/s and capacity stays at 400/s. Which change can stop unbounded backlog growth immediately?" options={[
  { id: "admit", text: "Admit no more than the sustainable rate and reject or defer excess work", correct: true, feedback: "Right. Bounded admission prevents accepted work from growing forever; increasing real capacity is another remedy." },
  { id: "queue", text: "Double the queue's memory limit", feedback: "That buys time but leaves the positive arrival-minus-completion rate unchanged." },
  { id: "retry", text: "Retry rejected work immediately without a limit", feedback: "Immediate retries raise offered load during overload and can worsen the backlog." }
]} />

</Step>

<Step id="closed-loop" title="Do not let the load test hide the queue">

A fixed-concurrency client sends less when the service slows. An open, rate-driven test keeps offering load. Use both.

<Compare title="Two load models" sides={[
  { title: "Closed loop", tone: "warn", points: ["Waits for replies", "Hides overload"] },
  { title: "Open arrival", tone: "ok", points: ["Constant rate", "Shows backlog and rejects"] }
]} />

<Choice id="load-generator" objective="identify-unstable-queue" prompt="Your ten-client test sends less traffic whenever latency rises. Production receives independently arriving webhooks. What additional test matters?" options={[
  { id: "open", text: "A bounded, rate-driven arrival test that continues offering the production rate", correct: true, feedback: "Right. It reveals whether backlog, rejection and latency remain controlled when arrivals do not wait for completions." },
  { id: "ignore", text: "Use only the ten-client test because it cannot queue", feedback: "The test can under-offer load precisely when production would continue accumulating arrivals." },
  { id: "average", text: "Publish the average latency without the offered rate", feedback: "Latency without load context cannot establish sustainable throughput." }
]} />

</Step>

<Step id="scale" title="Scaling one tier can expose the next bottleneck">

Stateless workers help only until a shared resource saturates.

<Choice id="shared-bottleneck" objective="estimate-service-capacity" prompt="Doubling web workers leaves throughput unchanged while database-pool wait grows. What does that suggest?" options={[

]} />

</Step>
