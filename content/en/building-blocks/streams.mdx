<Step id="time" title="An event has more than one clock">

An app records a purchase at 12:01, goes offline, then uploads it at 12:08. **Event time** is when the purchase occurred; **processing time** is when the pipeline handles it. Network delay, batching and replay can make their order differ.

If the report asks what customers bought during 12:00–12:05, processing-time grouping would misplace this purchase. Event-time grouping respects its timestamp but needs a policy for late arrival. Validate timestamps at ingestion: an untrusted clock far in the future can distort progress estimates and state retention.

<Step id="windows" title="A window boundary needs a convention">

A tumbling window is fixed-width and non-overlapping. We use **[start, end)**: include the start and exclude the end. With width 60 seconds and alignment at epoch zero, timestamp 125 belongs to **[120, 180)**. Timestamp 180 belongs to the next window.

The formula is **start = floor(timestamp / width) × width**. State the alignment as well as the width: calendar days in a local timezone are not always 24 hours across daylight-saving transitions. These questions use integer epoch seconds so boundary arithmetic stays explicit.

<Step id="window-types" title="Choose the grouping the question asks for">

Sliding windows overlap. A five-minute window emitted every minute can include one event in several outputs. Do not sum overlapping outputs as if they counted disjoint events. Session windows instead join activity separated by less than a configured inactivity gap; late data can merge sessions previously thought separate.

Choose a window for the product question, not merely for a convenient timer. Tumbling minutes fit non-overlapping per-minute totals. A rolling five-minute abuse detector needs overlapping or continuously updated state. Session duration needs a gap rule and a policy for late bridging events.

<Step id="watermark" title="A watermark estimates progress">

A watermark says how far an input estimates event time has progressed. It helps decide when to emit results or clean up old state. It is not a physical barrier preventing an older event from arriving after a slow device reconnects.

For an operator that waits on several inputs, the slowest relevant input can constrain progress. An idle partition may hold the watermark back unless the runner has an explicit idleness policy. Advancing aggressively lowers latency but can classify more events as late; waiting longer improves completeness at the cost of state and delayed results.

<Step id="late-data" title="Late events need a visible result policy">

Suppose a window ends at event time 120 seconds and allowed lateness is 30 seconds. Under our stated policy, retain state until the watermark reaches **150 seconds**. Events arriving during retention can revise the output; after cleanup they take the configured drop, side-output or reconciliation path.

Separate emission from cleanup. An early result can be useful while it is still provisional. An accumulating update should replace the prior value for that key and window; treating each updated total as a new increment double-counts. Label finality and record dropped late data so the report's completeness is observable.

<Step id="dedup" title="Deduplication spends bounded state">

At 500 new IDs/s, retaining IDs for ten minutes holds about **300,000 IDs** at steady rate. With 64 bytes per entry, that is **19.2 MB** before any excluded allocation overhead. Replication and checkpoint copies add more.

Choose a stable event ID rather than a fresh delivery ID. Set retention from the replay and lateness horizon: a duplicate arriving after its ID expires can be accepted again. Unlimited retention is not free, and a short TTL is not a lifetime exactly-once guarantee. Partition deduplication by a key that routes repeated IDs to the same authority.

<Step id="sink" title="Replay safety must reach the sink">

A processor can restore its checkpoint and replay input after failure. If it already sent an external payment or incremented a separate database before the crash, replay can repeat that effect. Processing state, input position and sink commit need compatible recovery rules.

For window totals, an idempotent upsert keyed by metric, entity and window can replace a prior total. Include a version rule so an older retry cannot overwrite a newer correction. If the sink accepts only increments, send uniquely identified deltas with atomic deduplication instead of repeatedly adding the entire revised total.
