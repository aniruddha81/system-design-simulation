<Step id="blob-and-metadata" title="Store bytes by key">

<Sequence title="Upload a photo" actors={["Client", "Object store", "Database"]} messages={[

An object holds bytes plus metadata under a key in a bucket. Keep searchable application metadata in a database. Prefer a new key for each blob version. Uploading bytes and publishing a database pointer are separate operations: reconcile orphan uploads and dangling pointers.

<Choice id="photo-layout" objective="blob-model" prompt="Which layout fits a photo service that searches by owner?" options={[

  { id: "early", text: "Publish pointers before upload succeeds, without repair", feedback: "Readers can receive pointers to bytes that do not exist." }
]} />

<Step id="two-promises" title="Kept safely does not mean reachable now">

<Compare title="Two separate questions" sides={[
  { title: "Durability", points: ["Will the stored object survive?", "Loss is permanent"] },
  { title: "Availability", points: ["Can a request succeed now?", "An outage may be temporary"] }
]} />

A network outage can make intact objects unavailable. Permanent loss harms durability even if other requests succeed. Durability estimates, availability targets and request measurements have different denominators and time horizons; do not convert one into the other.

<Choice id="outage-or-loss" objective="durability-availability" prompt="All fragments remain intact, but an outage blocks reads for ten minutes. What is demonstrated?" options={[
  { id: "unavailable", text: "An availability failure without demonstrated permanent data loss", correct: true, feedback: "Objects can survive while requests cannot reach them." },
  { id: "lost", text: "Permanent object loss", feedback: "Unreachable bytes have not necessarily been destroyed." },
  { id: "equal", text: "Durability equals the request success rate", feedback: "These metrics measure different events over different horizons." }
]} />

</Step>

<Step id="replicas" title="Three copies cost three times the bytes">

<Stats title="Ideal three-way replication" items={[
  { label: "Logical data", value: "100 GB", sub: "Before replication" },
  { label: "Stored bytes", value: "300 GB", sub: "3 complete copies" },
  { label: "Ideal tolerance", value: "2 copy losses", sub: "One intact reachable copy remains" }
]} />

Replication stores complete copies. Three copies have 3x raw storage overhead. Placement matters: three copies on one rack do not survive a rack loss. Repair must restore redundancy before further failures exhaust it.

<Choice id="replica-size" objective="coding-overhead" prompt="Ignoring metadata, how much raw capacity holds 200 GB with three complete replicas?" options={[
  { id: "one", text: "200 GB", feedback: "This counts only one copy." },
  { id: "two", text: "400 GB", feedback: "This counts two copies, not three." },
  { id: "three", text: "600 GB", correct: true, feedback: "200 GB times three copies is 600 GB." }
]} />

</Step>

<Step id="erasure-coding" title="Recover from a subset of fragments">

<Stats title="Example: k=6 data, m=3 parity" items={[
  { label: "Fragments", value: "9", sub: "Any 6 suffice for this ideal code" },
  { label: "Overhead", value: "1.5x", sub: "(6 + 3) / 6" },
  { label: "100 GB logical", value: "150 GB raw", sub: "Up to 3 fragment erasures per group" }
]} />

An ideal maximum-distance-separable code reconstructs from any k of k+m fragments. Raw overhead is (k+m)/k. It tolerates m fragment erasures per group, not arbitrary failures of m regions. Reconstruction and repair consume compute and bandwidth. Placement still determines which failures destroy too many fragments together.

<Choice id="coding-math" objective="coding-overhead" prompt="For k=8 and m=4, what stores 400 GB logically, ignoring metadata?" options={[
  { id: "coded", text: "600 GB raw; tolerate up to 4 fragment erasures per group", correct: true, feedback: "The multiplier is 12/8 = 1.5; any 8 surviving fragments reconstruct." },
  { id: "copies", text: "4800 GB raw; tolerate 8 erasures", feedback: "Fragments are portions, not 12 complete copies; the erasure budget is m=4." },
  { id: "regions", text: "400 GB raw; tolerate any 4 regional outages", feedback: "Parity adds capacity, and fragment placement determines regional tolerance." }
]} />

</Step>

<Step id="cost-model" title="Delivery can cost more than retention">

<Stats title="Invented monthly rates; decimal GB" items={[
  { label: "Storage", value: "USD 20", sub: "1,000 GB-month x USD 0.02" },
  { label: "Egress", value: "USD 450", sub: "5,000 GB x USD 0.09" },

Separate stored GB-month from transferred GB. Use provider-billed storage: do not multiply by internal redundancy again when included in the rate. Download frequency and cache misses drive egress. These prices are teaching inputs, not current market rates.

<Step id="choose-a-layout" title="Choose a layout for the workload">

<Compare title="Illustrative trade-offs" sides={[
  { title: "Full replicas", points: ["Read from a complete copy", "Higher raw byte overhead"] },
  { title: "Erasure coding", points: ["Lower raw byte overhead", "Reconstruction when fragments are missing"] },
  { title: "Both need", points: ["Failure-domain placement", "Repair capacity", "Measured availability"] }

A cold archive may favor coding efficiency; a small hot object may favor simpler reads. Neither choice alone proves a durability target. Test degraded reads, repair load and failure-domain placement against the workload.
