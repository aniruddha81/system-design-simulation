<Step id="why-cache" title="A database that cannot keep up">

A database answers in about 5 ms and saturates at a few thousand reads/s. A cache answers in under 1 ms, for keys it holds. **Hit rate** = share of reads the cache answers.

<Step id="db-load" title="Predict the database load">

<Step id="read-path" title="Follow a miss through cache-aside">

<Step id="skew" title="Where the hit rate comes from">

**Key popularity makes hits.** Reads are roughly Zipf: the top *k* of *N* keys get about **H(k) / H(N)** of requests. A cache of 1% of keys can serve over half the reads, and LRU nearly holds them.

<Flow title="Skewed reads" height={170} hot={["hot"]} nodes={[

<Step id="freshness" title="Keep cached data fresh">

A cached value is a copy and can go stale. **TTL** bounds staleness by time. **Invalidation**: the writer deletes the key after the database write.

<Compare title="Freshness levers" sides={[
  { title: "Long TTL", tone: "bad", points: ["Cheap", "Old data for hours"] },
  { title: "Delete on write + TTL", tone: "ok", points: ["Fresh within delete latency", "TTL is the safety net"] },
  { title: "Very short TTL", tone: "warn", points: ["Always misses", "More DB load"] }
]} />

<Choice
  id="price-freshness"
  objective="choose-freshness"
  prompt="Product prices change a few times a day. A price that is stale for more than a few seconds causes refunds. All price writes go through one pricing service. What do you do?"
  options={[
    { id: "long-ttl", text: "Cache prices with a 24-hour TTL", feedback: "A long TTL serves an old price for up to a day after each change. TTL alone bounds staleness by time, and a day is far too long here." },
    { id: "invalidate", text: "Delete the key in the pricing service after each database write, and keep a TTL as a safety net", correct: true, feedback: "Right. The writer knows exactly when data changes, so invalidation bounds staleness by the delete's latency. The TTL cleans up if a delete is ever lost." },
    { id: "short-ttl", text: "Use a 1-second TTL on every price", feedback: "This does bound staleness, but every key now misses every second. The hit rate drops and database load rises for data that changes a few times a day." },
    { id: "update-first", text: "Write the new price to the cache, then to the database", feedback: "If the database write fails, or a concurrent writer commits later, the cache holds a price the database never committed." }
  ]}
/>

</Step>

<Step id="stampede" title="The stampede after a restart">

A node restarts empty. Every hot key misses at once; a database sized for 95% hits sees nearly all traffic: a **stampede**.

<Timeline title="Cold restart" events={[
  { at: "t0", label: "Cache node restarts empty", tone: "bad" },
  { at: "t0 + 1 s", label: "Every request misses; DB saturates", tone: "bad" },
  { at: "Later", label: "Cache refills, hit rate recovers", tone: "ok" }
]} />

</Step>

<Step id="stampede-fix" title="Prevent the stampede">

**Leases** (Facebook memcache) or **request coalescing**: the first miss fills the key, others wait and retry the cache.

<Flow title="Coalesced misses" height={170} nodes={[
  { id: "r", label: "1,000 requests, same key", kind: "client", x: 0, y: 50 },
  { id: "s", label: "Single-flight", kind: "service", x: 50, y: 50, note: "one fill" },
  { id: "db", label: "Database", kind: "database", x: 100, y: 50, note: "1 query" }
]} edges={[{ from: "r", to: "s" }, { from: "s", to: "db", label: "one read" }]} />

<Choice
  id="stampede-mitigations"
  objective="explain-stampede"
  multiple
  prompt="After a cache node restart, the database is overwhelmed. Which changes reduce the stampede? Select all that apply."
  options={[
    { id: "coalesce", text: "Coalesce concurrent misses for the same key so one request fills it", correct: true, feedback: "Right. Database queries per hot key drop from rate × fill time to about one." },
    { id: "jitter", text: "Add random jitter to TTLs", correct: true, feedback: "Right. Keys written together otherwise expire together, which is a small stampede on a timer." },
    { id: "warm", text: "Pre-warm the hottest keys, or shift traffic back gradually", correct: true, feedback: "Right. Filling the cache before full load arrives keeps the miss rate low while it warms." },
    { id: "retry", text: "Retry failed database reads immediately", feedback: "Immediate retries add load exactly when the database is saturated. That turns a stampede into a retry storm." },
    { id: "short-ttl", text: "Shorten every TTL so stale data clears faster", feedback: "Shorter TTLs cause more misses, which means more database load, not less." }
  ]}
/>

</Step>
