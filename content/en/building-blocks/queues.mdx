<Step id="boundary" title="Accepted is not processed">

A checkout service publishes a receipt job and responds before an email worker runs. The queue decouples their timing, but the publish acknowledgement means only what the broker's configured durability policy promises. It does not prove the email was sent or the consumer's database transaction committed.

Use a durable queue and the appropriate publisher confirmation when the job must survive a broker failure. If an order commit and publish must occur together, two separate successful calls are not atomic. A transactional outbox records the job with the order, then a relay publishes it; consumers still need to handle duplicates.

  { id: "email", text: "The recipient received the email exactly once", feedback: "A publish confirmation does not wait for the consumer or the external email system." },
  { id: "atomic", text: "The producer's unrelated database commit is atomic with the publish", feedback: "Separate database and broker operations need a coordination pattern; a broker acknowledgement cannot combine them automatically." }
]} />

</Step>

<Step id="backlog" title="A burst spends queue space">

An empty queue receives 600 jobs/s while workers finish 400/s for 30 seconds. It accumulates **(600 − 400) × 30 = 6,000 jobs**. The queue buys time during a finite burst; it does not make sustained demand disappear.

Estimate bytes and age as well as message count. A queue of large exports may exhaust memory sooner than a much longer queue of small notifications. Reject or defer work before accepted jobs wait beyond their useful deadline, and make the acceptance contract clear to the producer.

</Step>

<Step id="drain" title="Spare capacity pays back the backlog">

After the burst, suppose arrivals fall to 300/s and workers still finish 400/s. Only **100/s** remains to drain old work, so 6,000 jobs take **60 seconds** to clear. Dividing by 400/s incorrectly assumes new arrivals stop.

Recovery capacity matters in failure planning. If normal traffic consumes every worker, a ten-minute outage can create a backlog that never drains. Increasing consumer count helps only while the downstream database and external APIs have spare capacity.

</Step>

<Step id="redelivery" title="The acknowledgement position chooses a failure window">

Acknowledging before processing risks losing work if the worker then crashes. Acknowledging after processing allows redelivery if the effect commits but the acknowledgement is lost. The latter is the familiar **at-least-once** pattern: a logical message may be delivered more than once.

Some brokers use visibility timeouts; others redeliver when the consumer's channel closes. In either case, do not assume the worker owns a message forever. Long-running work needs a suitable lease or timeout policy, and the effect must remain safe if another worker receives the message.

  { id: "transaction", text: "In one database transaction, record the ID and apply the effect only if it is new" },
  { id: "commit", text: "Commit the database transaction" },
  { id: "ack", text: "Acknowledge successful processing to the broker" }

<Step id="once" title="Exactly once needs an explicit boundary">

An idempotent consumer can provide an **effectively-once business effect** on top of at-least-once delivery. A unique operation ID prevents a duplicate database mutation when checked and committed atomically with that mutation. An in-memory set lost on restart cannot provide that guarantee.

A streaming system's transactional consume-transform-produce guarantee has a defined scope. It does not automatically include an unrelated payment API or email service. For external effects, use their idempotency support or a reconciliation workflow, and choose dedup retention long enough for the possible replay horizon.

<Choice id="effect-boundary" objective="distinguish-delivery-guarantees" prompt="A worker charges a card, crashes before acknowledging, then receives the job again. Which protects against a second charge?" options={[
  { id: "provider", text: "Reuse a stable payment operation key that the payment service enforces durably", correct: true, feedback: "Right. The deduplication boundary must include the external charge, not just local message receipt." },
  { id: "memory", text: "Keep a process-local set of message IDs", feedback: "The set disappears on crash and cannot establish whether the external charge happened." },
  { id: "ack-first", text: "Acknowledge first and hope charging succeeds", feedback: "That changes duplicate risk into a loss window: a crash after acknowledgement can leave the job permanently unprocessed." }
]} />

</Step>

<Step id="ordering" title="Ordering is usually per partition">

A log can preserve append order within one partition. If all events for account 42 use the same partition key, its debit and credit events can be read in that order. There is no global order across unrelated partitions unless you add coordination.

Delivery order also differs from effect order: concurrent handlers may finish in reverse order, and a failed event may be retried after a later event. Use per-key sequential processing, version checks or a reorder buffer when the business invariant requires it. One hot key can limit parallelism even with many idle workers.

<Choice id="account-order" objective="preserve-queue-ordering" prompt="Balance updates for one account must apply in sequence, while different accounts can run concurrently. What is a suitable starting design?" options={[
  { id: "key", text: "Partition by account ID and preserve per-account effect order in the consumer", correct: true, feedback: "Right. Stable key routing gives a local ordering scope, and consumer scheduling must preserve it through retries." },
  { id: "random", text: "Choose a random partition for each event", feedback: "Events for one account can land on independent partitions and race." },
  { id: "all", text: "Put every account in one global sequential worker without considering throughput", feedback: "That preserves an unnecessary global order and prevents parallelism across independent accounts." }
]} />

</Step>

<Step id="poison" title="A dead-letter queue is a workflow, not a bin">

A malformed message may fail every attempt. Retry transient failures with a bounded delay policy; send persistent failures to a dead-letter queue after a defined attempt limit. Alert, retain the cause, fix the input or handler, and replay with the same operation ID.

Back-pressure limits admission when consumers or dependencies fall behind. Watch oldest-message age, redelivery rate, DLQ growth and processing errors. A rising retry rate increases effective arrivals; a consumer that immediately requeues poison messages can consume its entire capacity doing no useful work.

<Choice id="poison-policy" objective="handle-poison-messages" prompt="One invalid job fails on every attempt and is immediately redelivered. What should change?" options={[
  { id: "dlq", text: "Bound retries, preserve diagnostics in a DLQ, and provide an inspected replay path", correct: true, feedback: "Right. This stops the hot loop while keeping failed work visible and recoverable." },
  { id: "forever", text: "Retry immediately forever to maximize reliability", feedback: "Repeated deterministic failure wastes capacity and can starve valid jobs." },
  { id: "delete", text: "Silently drop every failure, including transient ones", feedback: "That hides lost work and prevents recovery; the policy should distinguish retryable and persistent failures." }
]} />

</Step>
