<Step id="contract" title="Limit the resource the request consumes">

A rate limiter decides whether a request may start. A concurrency limiter bounds work already in flight. Both can protect a service, but a fixed requests/s budget does not prevent a slow dependency from accumulating many active requests. Use the boundary that matches the constrained resource.

Define the subject and cost: per account, API key, IP, tenant or global service; one token per call or a weighted cost for expensive operations. IP-only policies can punish many users behind one NAT and can miss an attacker spread across many addresses. A user quota is also different from global overload protection.

<Choice id="concurrency-vs-rate" objective="design-distributed-limiter" prompt="Requests stay at 100/s, but a dependency slows from 20 ms to ten seconds and active work explodes. What additional control directly bounds the active work?" options={[
  { id: "concurrency", text: "A bounded concurrency or admission limit with an explicit rejection policy", correct: true, feedback: "Right. Active requests grow with time in the system; a concurrency cap directly bounds that resource." },
  { id: "same", text: "Keep only the same 100/s rate limit and assume concurrency is fixed", feedback: "At the same rate, longer service time raises in-flight work. Rate alone does not fix concurrency." },
  { id: "unlimited", text: "Queue every request without a bound", feedback: "That moves the growth into memory and waiting time rather than bounding the resource." }
]} />

</Step>

<Step id="tokens" title="A token bucket separates burst from sustained rate">

A token bucket has capacity B and refill rate r tokens/s. An idle bucket refills only up to B; requests consume their cost atomically. A full bucket can admit B one-token requests at once, while sustained traffic must fit the refill rate over the long run.

If capacity is 20, the balance is 4, refill is 3/s and the bucket is idle for five seconds, the new balance is **min(20, 4 + 3 × 5) = 19**. Idle time does not accumulate infinite credit. The RFC marker uses byte-denominated buckets; API limiters often use request-denominated tokens with the same accounting idea.

<Step id="wait" title="Compute eligibility without promising a queue">

If a request needs six tokens and an empty bucket refills two tokens/s, it becomes eligible in **three seconds**, assuming no competing requests and enough bucket capacity. A request costing more than capacity can never pass under that configuration.

Eligibility does not mean the limiter queues the request automatically. Many API limiters reject immediately so the caller decides when to retry. A shaping limiter waits in a bounded queue instead. Long waits can make requests useless, so apply deadlines and bound queued work.

<Step id="windows" title="Fixed windows have a boundary burst">

A fixed window resets a counter at aligned intervals. A client allowed 100 requests per minute can send 100 just before a boundary and 100 immediately after: **200 requests in a very short interval**. The rule is still obeyed within each clock minute.

A sliding log checks timestamps over a rolling interval and can enforce a strict rolling count, at memory and update cost. Sliding-window counters approximate the interval using buckets and weighting, so their error must be part of the contract. Use a monotonic elapsed-time basis where possible; wall-clock jumps should not create free quota.

<Step id="shaping" title="A leaky bucket smooths departure">

In this lesson, a leaky bucket is a bounded queue drained at a controlled rate. It smooths departures but adds waiting. A token bucket instead allows bursts up to its capacity. Some networking texts use “leaky bucket” for an equivalent metering formulation; ask whether a proposed algorithm delays, marks or rejects.

For a partner API that requires smooth delivery, a shaper may fit. For an interactive endpoint that permits a short burst but must respond quickly, a token bucket with immediate rejection may fit better. An algorithm name is less useful than its precise admission and delay behavior.

<Step id="distributed" title="A distributed balance needs one atomic decision">

Reading a balance, checking it and decrementing it in separate operations lets two callers spend the same token. Put refill, eligibility and consumption in one atomic update at the quota authority. Include the subject and policy in the key, and bound the lifetime and cardinality of idle keys.

Local buckets avoid a network hop but multiply a per-process budget when traffic spreads across processes. A shared store coordinates more precisely but adds latency and a dependency. Regional quota leases can reduce coordination cost while permitting bounded overshoot. Choose that bound explicitly rather than calling every deployment globally exact.

<Choice id="shared-token" objective="design-distributed-limiter" prompt="Two gateway instances read a shared balance of one token before either decrements it. Both accept. What is the root fix?" options={[
  { id: "atomic", text: "Make refill, check and decrement one atomic operation at the quota authority", correct: true, feedback: "Right. Both decisions must serialize around the same token balance." },
  { id: "faster", text: "Use a faster network while keeping separate read and decrement calls", feedback: "A shorter race window is still a race; speed does not establish atomicity." },
  { id: "cache", text: "Cache the shared token balance independently in every gateway", feedback: "Independent cached balances can spend the same shared quota multiple times." }
]} />

</Step>

<Step id="failure" title="Fail-open and fail-closed are product decisions">

When a quota store fails, fail-open preserves access but can expose a scarce downstream resource. Fail-closed protects quota but may block legitimate users. A bounded local fallback can be appropriate when its aggregate overshoot is acceptable. Payments, login abuse and public content may need different policies.

For a quota rejection, HTTP **429 Too Many Requests** communicates the condition; `Retry-After` can give retry guidance. Clients should respect it, use bounded backoff and jitter, and stop at their deadline. Retrying instantly from every client recreates the overload the limiter is trying to prevent.

<Choice id="retry-limiter" objective="communicate-rate-limit" prompt="A client receives 429 with Retry-After: 5. What should its retry policy do?" options={[

  { id: "new-key", text: "Rotate user identities to bypass the quota", feedback: "That defeats the policy and turns ordinary retry behavior into quota evasion." }
]} />
