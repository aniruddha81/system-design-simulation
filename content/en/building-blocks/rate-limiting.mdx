<Step id="contract" title="Limit the resource the request consumes">

A rate limiter decides whether a request may **start**. A concurrency limiter bounds work **in flight**. Pick the one that matches the constrained resource, and a subject (account, key, tenant) and cost per call. IP-only limits punish shared NATs.

<Compare title="Same rate, slow dependency" sides={[
  { title: "Rate limit only", tone: "bad", points: ["100/s still admitted", "In-flight work explodes at 10 s each"] },
  { title: "Plus concurrency cap", tone: "ok", points: ["Bounds active work", "Explicit rejection policy"] }
]} />

<Choice id="concurrency-vs-rate" objective="design-distributed-limiter" prompt="Requests stay at 100/s, but a dependency slows from 20 ms to ten seconds and active work explodes. What additional control directly bounds the active work?" options={[
  { id: "concurrency", text: "A bounded concurrency or admission limit with an explicit rejection policy", correct: true, feedback: "Right. Active requests grow with time in the system; a concurrency cap directly bounds that resource." },
  { id: "same", text: "Keep only the same 100/s rate limit and assume concurrency is fixed", feedback: "At the same rate, longer service time raises in-flight work. Rate alone does not fix concurrency." },
  { id: "unlimited", text: "Queue every request without a bound", feedback: "That moves the growth into memory and waiting time rather than bounding the resource." }
]} />

</Step>

<Step id="tokens" title="A token bucket separates burst from sustained rate">

Bucket capacity B, refill r/s. Idle time refills only up to B.

<Step id="wait" title="Compute eligibility without promising a queue">

Six tokens at 2 tokens/s from empty: eligible in **3 s**. A cost above capacity never passes. Most API limiters reject now and let the caller retry; a shaper queues, with a bound.

]} />

<Step id="windows" title="Fixed windows have a boundary burst">

A fixed window resets at aligned times, so a client can spend two windows back to back. A sliding log is strict but costs memory; sliding counters approximate.

<Timeline title="100 per minute, fixed window" events={[
  { at: "0:59", label: "100 requests", tone: "info" },

  { at: "1:01", label: "100 more: 200 in 2 s", tone: "bad" }
]} caption="Use monotonic time so clock jumps cannot grant free quota." />

<Step id="shaping" title="A leaky bucket smooths departure">

A **leaky bucket** here is a bounded queue drained at a fixed rate: smooth, but adds wait. A **token bucket** allows bursts. Ask whether an algorithm delays, marks or rejects.

<Compare title="Shape or meter" sides={[
  { title: "Leaky bucket (shaper)", tone: "info", points: ["Smooth output", "Adds waiting", "Expire stale jobs"] },
  { title: "Token bucket (meter)", tone: "ok", points: ["Burst up to B", "Reject immediately", "Fast interactive replies"] }
]} />

<Choice id="limiter-shape" objective="choose-limiter" prompt="A partner accepts at most a smooth ten jobs/s, and jobs can wait up to two seconds. Which design is a useful fit?" options={[
  { id: "leaky", text: "A bounded queue drained at ten jobs/s, with expiry for jobs exceeding the deadline", correct: true, feedback: "Right. A shaper regulates departure timing while the bound and expiry keep waiting controlled." },
  { id: "burst", text: "A token bucket holding 10,000 tokens sent as an immediate burst", feedback: "That permits a large instantaneous arrival burst at the partner, which conflicts with smooth delivery." },
  { id: "infinite", text: "An unbounded queue with no job deadline", feedback: "That can smooth departures but violates the bounded-wait requirement during sustained overload." }
]} />

</Step>

<Step id="distributed" title="A distributed balance needs one atomic decision">

Read, check and decrement as separate calls lets two callers spend one token. Do refill, check and consume atomically at the quota authority.

<Sequence title="Race on the last token" actors={["Gateway 1", "Quota store", "Gateway 2"]} messages={[
  { from: "Gateway 1", to: "Quota store", label: "read: 1 token" },
  { from: "Gateway 2", to: "Quota store", label: "read: 1 token" },
  { from: "Gateway 1", to: "Quota store", label: "decrement, accept", tone: "bad" },
  { from: "Gateway 2", to: "Quota store", label: "decrement, accept", tone: "bad" }
]} caption="Local buckets multiply the budget. Regional leases bound the overshoot." />

<Choice id="shared-token" objective="design-distributed-limiter" prompt="Two gateway instances read a shared balance of one token before either decrements it. Both accept. What is the root fix?" options={[
  { id: "atomic", text: "Make refill, check and decrement one atomic operation at the quota authority", correct: true, feedback: "Right. Both decisions must serialize around the same token balance." },
  { id: "faster", text: "Use a faster network while keeping separate read and decrement calls", feedback: "A shorter race window is still a race; speed does not establish atomicity." },
  { id: "cache", text: "Cache the shared token balance independently in every gateway", feedback: "Independent cached balances can spend the same shared quota multiple times." }
]} />

</Step>

<Step id="failure" title="Fail-open and fail-closed are product decisions">

If the quota store fails: fail-open risks the downstream; fail-closed blocks real users. Decide per product (payments, login, public content).

On a rejection send **429** with `Retry-After`. Clients back off with jitter and stop at their deadline.

<Choice id="retry-limiter" objective="communicate-rate-limit" prompt="A client receives 429 with Retry-After: 5. What should its retry policy do?" options={[
