<Step id="families" title="Start with the access pattern">

<Compare title="Database families" sides={[{"title": "Relational SQL", "points": ["Relations, joins and constraints", "Flexible indexed queries"]}, {"title": "Key-value / document", "points": ["Key lookups / aggregate documents", "Indexes depend on engine"]}, {"title": "Wide-column / graph", "points": ["Partition-key and range access", "Or relationship traversal"]}]} />

NoSQL covers multiple families, not one feature set. Key-value stores suit keyed access; documents group nested data; wide-column stores organize partitioned rows; graph databases emphasize relationships. SQL systems can also store JSON. Choose from query shape, invariants and operational needs.

<Step id="family-boundaries" title="Avoid a label-based guarantee">

<Compare title="Two access patterns" sides={[{"title": "Session lookup", "points": ["Read by opaque session id", "TTL expiration useful"]}, {"title": "Relationship traversal", "points": ["Find paths across many hops", "Edge traversal is central"]}]} />

A key-value store is a natural fit for simple keyed sessions. A graph model may fit multi-hop relationships. Neither label guarantees transactions, scale or speed. Measure the actual workload and verify durability and consistency requirements separately.

<Step id="scan-index" title="Compare examined rows with returned rows">

<Bars title="Illustrative selective query over 1,000,000 rows" items={[{"label": "Full scan: examined rows", "value": 1000000, "unit": "rows"}, {"label": "Indexed: matching rows fetched", "value": 10, "unit": "rows"}]} />

A full scan examines the table. A suitable B-tree index navigates to a key range, then reads matches. A rough comparison is O(N) versus O(log N + K), where K is returned entries. Index traversal and heap fetches still cost work; this picture is not a latency benchmark.

<Step id="index-selectivity" title="A usable index can still lose">

<Compare title="Planner choices" sides={[{"title": "Selective predicate", "points": ["Few matches", "Index path often useful"]}, {"title": "Most rows match", "points": ["Many scattered row fetches", "Sequential scan may win"]}]} />

Indexes consume storage and add write work. They help only when their ordering and predicates support the query. If most rows match, sequential I/O can beat many random fetches. EXPLAIN shows the chosen plan; EXPLAIN ANALYZE executes it and measures actual work.

<Step id="btree" title="Update ordered pages">

<Compare title="B-tree organization" sides={[{"title": "Read path", "points": ["Navigate internal pages", "Read ordered leaf entries"]}, {"title": "Write path", "points": ["Modify affected pages", "Split pages when required"]}]} />

B-tree indexes maintain ordered pages, supporting equality and range scans. Updates modify affected pages and may cause splits; databases typically add logging and buffering. Every additional secondary index adds maintenance. Ordered lookup does not make writes free or define the transaction isolation level.

<Step id="lsm" title="Buffer, flush and merge">

<Timeline title="Simplified LSM lifecycle" events={[{"at": "Write", "label": "Log for durability; insert into memory table"}, {"at": "Flush", "label": "Write a sorted immutable file"}, {"at": "Compact", "label": "Merge sorted files; discard obsolete versions when safe"}]} />

An LSM engine buffers writes and flushes sorted runs. Compaction merges those runs, rewriting data to control overlap and space. Reads may consult memory and multiple files; Bloom filters and indexes can reduce probes. LSMs trade read, write and space amplification through policy choices.

<Step id="write-amplification" title="Measure physical work per logical byte">

<Bars title="Illustrative measured amplification for 100 MB logical writes" items={[{"label": "Logical writes", "value": 100, "unit": "MB"}, {"label": "Engine A: 3x", "value": 300, "unit": "MB physical"}, {"label": "Engine B: 8x", "value": 800, "unit": "MB physical"}]} />

**Write amplification = physical bytes written / logical bytes written.** At 8?, 100 MB becomes 800 MB. Compare the same measurement boundary: device writes, engine writes and logged bytes differ. Neither B-tree nor LSM has one universal factor; workload, compaction, page size and compression matter.
