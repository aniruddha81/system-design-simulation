<Step id="api-shapes" title="Choose the contract shape">

<Compare title="Three API contracts" sides={[{"title": "REST", "points": ["Resource identifiers", "HTTP method semantics"]}, {"title": "gRPC", "points": ["Typed service methods", "Generated clients; streaming"]}, {"title": "GraphQL", "points": ["Typed graph schema", "Client selects response fields"]}]} />

REST is an architectural style, not just JSON over HTTP. gRPC exposes typed procedures. GraphQL lets clients select graph fields; the server still owns authorization, query cost and data access.

<Step id="graphql-boundaries" title="Keep flexible queries bounded">

<Compare title="One product screen" sides={[{"title": "REST resources", "points": ["GET product", "GET reviews"]}, {"title": "GraphQL operation", "points": ["Select product and reviews", "Resolvers may still fan out"]}]} />

A single GraphQL request can trigger many backend reads. Field selection can reduce overfetching, but query depth, resolver batching, authorization and cost limits remain server responsibilities.

<Choice
  id="graphql-boundaries-check"

<Step id="live-updates" title="Pick a live-update transport">

<Compare title="Connection direction" sides={[{"title": "WebSocket", "points": ["Two-way messages", "Long-lived connection"]}, {"title": "SSE", "points": ["Server to browser events", "HTTP event stream; reconnect"]}, {"title": "Long polling", "points": ["Hold response until update", "Client issues next request"]}]} />

WebSockets suit two-way interaction. SSE suits server-driven feeds; browser EventSource can reconnect and carry event IDs. Long polling holds an ordinary HTTP request until an event or timeout, then repeats. Every option needs reconnect and overload behavior.

<Choice
  id="live-updates-check"
  objective="choose-transport"
  prompt="A dashboard only receives server alerts and should use the browser EventSource API. Choose a transport."
  options={[{"id": "option-3", "text": "Long polling because it never repeats requests", "feedback": "Long polling starts another request after each response or timeout."}, {"id": "option-1", "text": "SSE", "feedback": "EventSource consumes server-sent event streams; retained event IDs can support resumption.", "correct": true}, {"id": "option-2", "text": "WebSocket because SSE sends only one event", "feedback": "SSE can deliver many events over one response."}]}
/>

</Step>

<Step id="pagination" title="Notice offset drift">

<Timeline title="Newest-first list changes between pages" events={[{"at": "Page 1", "label": "Read A, B at offset 0"}, {"at": "Insert", "label": "X arrives before A"}, {"at": "Page 2", "label": "Offset 2 returns B, C: B repeats"}]} />

Offset pagination names a position that can move. A cursor names a boundary in a stable total order, such as (created_at, id). Fetch after that boundary using the same filters and ordering. Cursors avoid this insertion shift, but do not create a snapshot.

<Choice
  id="pagination-check"
  objective="paginate-safely"
  prompt="How should a newest-first feed cursor handle equal timestamps?"
  options={[{"id": "option-1", "text": "Include a unique tie-breaker such as id", "feedback": "The timestamp plus id defines an unambiguous total order.", "correct": true}, {"id": "option-2", "text": "Store only the timestamp", "feedback": "Equal timestamps leave the next-page boundary ambiguous."}, {"id": "option-3", "text": "Use a larger offset", "feedback": "A larger offset still shifts when earlier rows are inserted."}]}
/>

</Step>

<Step id="compatibility" title="Evolve without stranding clients">

<Compare title="Response change" sides={[{"title": "Usually additive", "points": ["New optional field", "Old clients tolerate unknown fields"]}, {"title": "Breaking", "points": ["Rename required field", "Change meaning or type"]}]} />

Compatibility includes behavior, not just schemas. Additive fields are safe only when readers tolerate them. New enum values can break exhaustive clients. Use a migration window and explicit version boundary for incompatible changes; retire old versions only after client migration.

<Choice
  id="compatibility-check"
  objective="evolve-contract"
  prompt="An old mobile app requires total_cents. You want a new money object. What preserves it during migration?"
  options={[{"id": "option-2", "text": "Rename total_cents immediately", "feedback": "Deployed apps still read the old name and can fail."}, {"id": "option-3", "text": "Keep the name but change cents to dollars", "feedback": "The type may stay numeric while the meaning breaks payments."}, {"id": "option-1", "text": "Keep total_cents and add the new representation during migration", "feedback": "Existing readers retain their contract while clients migrate.", "correct": true}]}
/>

</Step>

<Step id="idempotency" title="Retry one logical operation">

<Sequence title="Acknowledgment lost" actors={["Client", "API", "Store"]} messages={[{"from": "Client", "to": "API", "label": "Create order, key K"}, {"from": "API", "to": "Store", "label": "Atomically record effect + result for K"}, {"from": "Client", "to": "API", "label": "Retry same payload, key K"}, {"from": "API", "to": "Client", "label": "Replay stored result; no second order"}]} />

An idempotency key identifies one logical operation. Scope it to the caller and operation, bind it to the request payload, and retain its result. Concurrent requests require atomic deduplication with the effect. Reusing a key with a different payload must be rejected.

<Choice
  id="idempotency-check"
  objective="deduplicate-retries"
  prompt="The order committed but its response was lost. How should the client retry?"
  options={[{"id": "option-3", "text": "Use the same key for every future order", "feedback": "Distinct orders need distinct keys; payload mismatches must not replay an unrelated result."}, {"id": "option-1", "text": "Send the same payload and the same key within the retention window", "feedback": "The server can return the recorded result without creating another order.", "correct": true}, {"id": "option-2", "text": "Generate a fresh key for each attempt", "feedback": "A fresh key looks like a new logical operation."}]}
/>

</Step>

<Step id="retention" title="Expose the retry boundary">

<Timeline title="Example documented key retention" events={[{"at": "t0", "label": "K creates one order"}, {"at": "t0 + 1 hour", "label": "Retry K replays result"}, {"at": "t0 + 25 hours", "label": "24-hour retention has expired"}]} />

Deduplication is bounded by retention. After expiry, the same key may be treated as new. Persist a business identifier when duplicate effects must remain impossible beyond that window. A transport retry policy cannot supply permanent exactly-once business behavior.
