<Step id="atomic" title="Atomic is not the same as isolated">

**Atomicity**: commit or abort as a unit. **Isolation**: what concurrent transactions can see. **Durability**: survives failure after ack. None sends an email atomically. Write the invariant first.

  { from: "Txn 2", to: "Database", label: "seat A12 free?" },
  { from: "Txn 1", to: "Database", label: "reserve A12", tone: "bad" },
  { from: "Txn 2", to: "Database", label: "reserve A12", tone: "bad" }
]} caption="Each commits atomically; the invariant still breaks." />

<Choice id="atomic-isolation" objective="protect-transaction-invariant" prompt="Two atomic transactions each read that a seat is free, then both create a reservation. What is missing from the claim that atomicity alone makes this safe?" options={[
  { id: "invariant", text: "A concurrency rule or constraint that prevents two reservations for the same seat", correct: true, feedback: "Right. All-or-nothing writes do not by themselves serialize competing decisions." },
  { id: "larger", text: "A larger server, which guarantees isolation", feedback: "Faster hardware can change timing, but it does not establish a correctness rule for concurrent transactions." },
  { id: "tls", text: "TLS encryption between clients and the database", feedback: "Encryption protects transport; it does not arbitrate conflicting reservations." }
]} />

</Step>

<Step id="lost-update" title="A read-modify-write can erase another update">

Read 10, both write 11: **lost update**. Fix with `value = value + 1` or a version predicate, then check the affected-row count.

<Sequence title="Lost update" actors={["Client A", "Row", "Client B"]} messages={[
  { from: "Client A", to: "Row", label: "read 10" },
  { from: "Client B", to: "Row", label: "read 10" },
  { from: "Client A", to: "Row", label: "write 11" },
  { from: "Client B", to: "Row", label: "write 11 (A's update erased)", tone: "bad" }
]} caption="Zero rows affected means conflict: re-read and retry. It is not success." />

<Choice id="lost-update-fix" objective="compare-concurrency-control" prompt="An optimistic UPDATE includes WHERE version = 7 and affects zero rows. What should the caller do?" options={[
  { id: "retry", text: "Treat it as a conflict and re-read before retrying the decision", correct: true, feedback: "Right. The stale precondition failed; recompute from current state or return a conflict." },
  { id: "success", text: "Report success because the SQL statement executed", feedback: "Execution without an affected row did not apply the requested state change." },
  { id: "overwrite", text: "Remove the version predicate and overwrite unconditionally", feedback: "That discards the check and can reintroduce the lost update the version was meant to prevent." }
]} />

</Step>

<Step id="write-skew" title="A snapshot can preserve reads and still break a rule">

Two doctors on call; each checks the other, then goes off. Different rows, so both commit and nobody is on call. This is **write skew**. Predict the invariant, then compare snapshot with serializable.

<Step id="reservation" title="Enforce the rule where the race happens">

Enforce the rule where the race happens: a **unique constraint** on the seat. A prior SELECT cannot stop a concurrent insert. Multirow rules need serializable transactions or a shared locked record. Retry on constraint and serialization failures, and keep side effects outside.

  { id: "b", label: "Request B", kind: "client", x: 0, y: 80 },
  { id: "d", label: "UNIQUE(seat)", kind: "database", x: 100, y: 50, note: "one insert wins" }
]} edges={[{ from: "a", to: "d" }, { from: "b", to: "d", label: "rejected", dashed: true }]} />

<Choice id="unique-seat" objective="protect-transaction-invariant" prompt="Two requests simultaneously reserve seat A12. Which directly enforces at most one active reservation in a simplified table with one row per reserved seat?" options={[
  { id: "unique", text: "A unique seat constraint, with conflict handling in the caller", correct: true, feedback: "Right. The constraint arbitrates concurrent inserts at the database boundary." },
  { id: "check", text: "SELECT for absence, then INSERT without any constraint", feedback: "Both transactions can observe absence before either insert commits." },
  { id: "cache", text: "Cache the fact that the seat looked free", feedback: "A cached observation is older evidence, not an atomic reservation authority." }
]} />

</Step>

<Step id="indexes" title="Isolation and storage structure answer different questions">

B-tree: ordered pages. LSM: buffer and merge sorted runs. Neither name tells you the isolation level.

**Write amplification = physical bytes written ÷ logical bytes updated.**
