<Step id="key" title="A shard key chooses where work lands">

Partitioning splits data; replication copies it. The shard key sets routing, locality and cross-shard work. Start from queries, not hash functions.

<Compare title="Shard key trade-offs" sides={[
  { title: "Tenant ID", tone: "ok", points: ["Tenant queries stay local", "Huge tenant dominates a shard"] },
  { title: "Random row ID", tone: "warn", points: ["Writes spread evenly", "Range queries hit every shard"] },
  { title: "Constant key", tone: "bad", points: ["All work on one shard"] }
]} />

<Choice id="shard-locality" objective="choose-shard-key" prompt="Most queries fetch all recent events for one tenant, and tenants are reasonably sized. Which initial key keeps those queries local?" options={[
  { id: "tenant", text: "Tenant ID, with a plan for unusually large tenants", correct: true, feedback: "Right. Tenant locality reduces fan-out, while the large-tenant exception remains a capacity concern." },
  { id: "random", text: "A new random shard for every event regardless of tenant", feedback: "That spreads load but scatters each tenant's query over the cluster." },
  { id: "same", text: "One constant key shared by every event", feedback: "A constant key sends all work to one shard and defeats partitioning." }
]} />

</Step>

<Step id="ring" title="Follow the ring clockwise">

`hash(key) % N` remaps most keys when N changes. On a ring, a key belongs to the first token clockwise, wrapping at the end. Virtual nodes smooth the intervals. Predict what moves, then add and remove nodes.

<HashRingPlayer seed={7} />

<Choice id="ring-owner" objective="explain-ring-routing" prompt="Tokens are at 10, 40 and 80 on a circular space from 0 to 99. Which token owns a key at 90?" options={[
  { id: "ten", text: "10, after wrapping around", correct: true, feedback: "Right. Ownership goes to the next token clockwise, including wraparound." },
  { id: "eighty", text: "80, because it is numerically nearest", feedback: "This routing rule is successor clockwise, not nearest absolute distance." },
  { id: "forty", text: "40, because it is near the middle", feedback: "The midpoint has no special role; follow clockwise from the key's hash." }
]} />

</Step>

<Step id="movement" title="Estimate how much data must move">

Adding a node to N balanced nodes moves about **1 / (N + 1)** of keys. This is an expectation, not a guarantee on a small ring; measure bytes too.

<Step id="rebalance" title="Ownership changes need a data protocol">

Changing the routing map copies no data. Use a versioned map, a catch-up path and a coordinated handoff. Rate-limit copying.

<Step id="tradeoffs" title="Partitioning moves coordination into the design">

Sharding moves coordination into your design: cross-shard uniqueness, joins and transactions cost more. Pick the smallest layout that meets measured need, and watch per-shard latency and key popularity.
