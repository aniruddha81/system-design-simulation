<Step id="key" title="A shard key chooses where work lands">

Partitioning splits a dataset across nodes. Replication copies it. A shard key controls routing, locality and which operations need cross-shard coordination. Start with the queries and invariants, not with a preferred hash function.

Putting an account's rows together makes account queries local, but a huge account may dominate its shard. Partitioning by a random row ID spreads writes but can scatter a range query across every shard. There is no universal shard key: choose the locality you need and expose the resulting skew and fan-out.

  { id: "same", text: "One constant key shared by every event", feedback: "A constant key sends all work to one shard and defeats partitioning." }
]} />

</Step>

<Step id="range" title="Range and hash partitioning fail differently">

Range partitioning keeps adjacent keys together and supports efficient range scans. A timestamp key can send every new write to the newest range. Splitting ranges helps distribute stored data, but an ever-moving write frontier can remain hot.

Hash partitioning spreads distinct keys more evenly but loses natural range locality. A request for all records in a time interval may require scatter-gather. Composite schemes can hash by tenant and range by time within a tenant, but the extra layout should solve a demonstrated workload need.

<Step id="ring" title="Follow the ring clockwise">

Simple `hash(key) % N` changes routing for many keys when N changes. Consistent hashing places both keys and node tokens on a circular hash space. A key belongs to the first node token clockwise, wrapping around at the end.

Add a node and only the intervals it takes change owner. Virtual nodes give one physical machine many tokens, reducing sensitivity to one unlucky large interval. They also add routing metadata and migration fragments. Predict which keys move, then use the focused model to add and remove nodes and compare with modulo routing.

<Step id="movement" title="Estimate how much data must move">

For N ideally balanced equal nodes, one added node should own about **1 / (N + 1)** of keys after rebalancing. Growing from four to five nodes moves about one fifth of existing keys. With ten million keys, that is approximately **two million** ownership changes.

This is an expectation under balance assumptions, not a guarantee for a small ring. Payload sizes, replication and token placement change copied bytes. A two-million-key migration may move very different volumes if one key holds a large object. Measure bytes and migration bandwidth as well as key counts.

<Step id="hot-key" title="Balanced keys can still mean unbalanced traffic">

Suppose one celebrity profile receives 30% of 20,000 reads/s. Its owner handles **at least 6,000 reads/s**, even if every other key is perfectly balanced. Virtual nodes redistribute intervals, not requests within that single key.

For reads, replication or a cache can spread demand. For writes, split an aggregatable counter or a tenant's data into subkeys only if the operation permits it. Splitting a key may sacrifice simple ordering or atomic updates, so a salting trick must come with a read and reconciliation plan.

</Step>

<Step id="rebalance" title="Ownership changes need a data protocol">

Updating the routing map does not copy data. During migration, old and new owners can disagree, and writes can arrive while a snapshot is in transit. A safe design needs a versioned ownership map, a change catch-up path and a defined handoff point.

One approach copies a snapshot, catches up changes, switches ownership under a coordinated protocol, then retains forwarding or fallback during the transition. Exact mechanics depend on the storage system. Rate-limit copying so rebalancing does not consume the spare capacity needed to serve traffic or recover from a failure.

<Step id="tradeoffs" title="Partitioning moves coordination into the design">

A unique username constraint on one shard is easy to enforce locally. A constraint spanning all shards needs routing to one authority or distributed coordination. Cross-shard joins and transactions also add network and failure cases. Do not shard only because a future scale number sounds large.

Choose the smallest layout that meets measured capacity and growth needs. Make the partition key part of data access patterns and observability: per-shard latency, bytes and key popularity show failures hidden by fleet averages. Keep an escape path for a large tenant before it becomes the whole incident.
