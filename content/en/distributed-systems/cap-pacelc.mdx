<Step id="what-cap-says" title="What the theorem actually says">

Brewer stated CAP as a conjecture in 2000; Gilbert and Lynch proved it in 2002 with precise definitions, and those definitions are the whole point:

- **Consistency** means *linearizability*: every operation appears to take effect at a single instant between its call and its return, so a read never returns a value older than a write that already completed. This is not the C in ACID.
- **Availability** means every request to a node that has not crashed eventually gets a non-error response. A timeout or "try again later" counts as unavailable.
- **Partition tolerance** means the system keeps its promises while the network drops an arbitrary set of messages between nodes.

The theorem: when a partition happens, a replicated store must give up one of C or A for the operations that cross it. You cannot opt out of partitions in a system that spans more than one machine, so "CA" is not a real third option. It only describes a system that has not yet met a partition.

<Step id="partition" title="Who loses availability, and how many">

"Giving up availability" sounds like an outage, but it is usually much narrower. Take a five-replica store that commits a write only when three replicas, a strict majority, have it. A partition cuts two replicas away from the other three.

The three-replica side still holds a majority and keeps committing. The two-replica side cannot form a majority, so to stay linearizable it must refuse writes and refuse reads it cannot prove are current. Only the clients stuck with the minority see errors. That is what etcd, ZooKeeper and every Raft- or Paxos-based store do.

<Step id="ap-side" title="The available choice, and its bill">

The alternative is to keep answering on both sides. Amazon's Dynamo did this for the shopping cart: an "add to cart" must never fail, so any reachable replica accepts the write, and the two sides diverge. When the partition heals, the system must reconcile. Dynamo returned all concurrent versions to the application, which merged carts by union. The known side effect: a deleted item could reappear, because a union cannot tell "removed on one side" from "never added on the other".

Availability is a real business choice, but it moves work to conflict resolution. Before you choose it, say what happens when both sides change the same thing.

<Step id="else-latency" title="PACELC: the trade-off you pay every day">

Partitions are rare. Abadi's 2012 observation is that the trade-off people actually feel is present all the time: **if there is a Partition, choose Availability or Consistency; Else, choose Latency or Consistency.**

Consistency costs latency because a write cannot be acknowledged until enough replicas have it, and replicas worth having are far apart. Put five replicas in five regions and require a majority: every write waits for the round trip to the second-nearest follower. Serve reads and writes from the local replica alone and you answer in microseconds, at the price of stale or conflicting data.

<Step id="classify" title="Classify a configuration, not a product">

PACELC gives two letters per configuration. Abadi's own examples: Dynamo-style stores such as Cassandra and Riak, in their default setup, are **PA/EL**: available under partition and low-latency otherwise. Fully consistent systems built on consensus are **PC/EC**. Yahoo's PNUTS was **PC/EL**: it kept a per-record master, so it gave up availability for that record under partition, but read from local replicas that could be stale.

Most modern stores let each request choose. A Cassandra read at consistency level ONE and a read at QUORUM are different points in the space, issued against the same cluster.

Select **quorum overlap** in Script and inspect the read and write sets. Then keep Sloppy quorum with spare replicas checked and select **sloppy quorum and hinted handoff**. A spare acknowledges for an unavailable home replica; watch the home-only read miss the write before handoff repairs it. R + W > N guarantees overlap only when both sets come from the same fixed replica group.

<Step id="beyond-cap" title="What CAP does not tell you">

CAP is a statement about one corner case, so it is easy to over-apply. In 2012 Brewer suggested designing for partitions explicitly instead: detect the partition, enter a partition mode that limits risky operations, and run a recovery step that merges state and repairs invariants afterwards. ATMs famously do this: offline, they still dispense cash up to a limit and reconcile later.
