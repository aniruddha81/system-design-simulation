<Step id="contract" title="A consistency model is a contract">

A consistency model is a rule about which **histories** a store may produce: which values each read is allowed to return, given the writes that happened around it. Stronger models allow fewer histories, which makes programs easier to reason about, and cost more coordination.

The strongest common single-object model is **linearizability** (Herlihy and Wing, 1990). Every operation appears to take effect atomically at some point between its invocation and its response, and those points respect real time. Once a write has returned, every read that *starts* later must see it or something newer.

  objective="order-models"

  options={[
    { id: "linear", text: "Linearizability", correct: true, feedback: "Right. The write completed before the read began, so in real-time order the read must return 1. B saw the past." },
    { id: "eventual", text: "Eventual consistency", feedback: "Eventual consistency only promises that replicas converge if writes stop. A stale read 2 ms later is allowed." },
    { id: "ryw", text: "Read-your-writes", feedback: "Read-your-writes constrains a session reading its own writes. B never wrote x, so this guarantee says nothing about B's read." },
    { id: "none", text: "None: B is on another continent, so it cannot know yet", feedback: "Physics is exactly why linearizability is expensive, not an exemption from it. A linearizable store would have made B's read wait or contact a replica that has the write." }
  ]}
/>

</Step>

<Step id="ladder" title="The ladder of models">

From strongest to weakest, for a single object:

- **Linearizable**: one global order that matches real time.
- **Sequential** (Lamport, 1979): one global order that every client agrees on and that respects each client's own program order, but it may disagree with real time across clients.
- **Causal**: everyone agrees on the order of causally related operations, meaning a write that depends on something its writer had read; concurrent writes may be seen in different orders by different readers.
- **Eventual**: if writes stop, replicas eventually converge. Nothing is said about what you see in the meantime.

The session guarantees of the next steps sit beside causal: causal consistency implies all four of them.

<Step id="sequential" title="Sequential is not linearizable">

The difference between the top two rungs is real time. Under sequential consistency, a single client sees its own operations in order, and all clients agree on one interleaving, but that interleaving can place a completed write after a later read.

  options={[

It contradicts real time, since A's write finished before B's first read began." },
    { id: "neither", text: "Neither sequential nor linearizable", feedback: "There is a single order everyone agrees on that respects each client's program order, which is all sequential consistency needs." },
    { id: "both", text: "Both sequential and linearizable", feedback: "Linearizability also respects real time. A read that starts after a completed write cannot return the older value." },
    { id: "causal-violation", text: "It violates causal consistency", feedback: "B had not observed A's write before reading 0, so there is no causal dependency being broken." }
  ]}
/>

</Step>

<Step id="session" title="Session guarantees, and how to build one">

Terry et al. (1994) named four guarantees a single client session can get from a weakly consistent store:

- **Read-your-writes**: a session sees its own earlier writes.
- **Monotonic reads**: once a session has seen a version, it never sees an older one.
- **Monotonic writes**: a session's writes apply in the order it issued them.
- **Writes-follow-reads**: a write is ordered after the writes its session had already read.

These guarantees are cheap because they only order one client's view. The standard implementation is a token: after each write, the session remembers the log position or timestamp it committed at, and a replica serves that session only once it has applied at least that far. A follower that is behind waits, or the request is routed elsewhere.

<Step id="violations" title="Spot the violation">

The most common real-world bug here is a load balancer that sends each read of one session to a different replica, with replicas at different lag. Nothing is "broken"; each replica is merely behind by a different amount. The user sees a comment appear, refreshes, and it is gone.

<Choice
  id="flip-flop"
  objective="identify-violation"
  prompt="A user who did not write anything reloads a page three times. Their reads return post version 7, then version 5, then version 7. Which guarantee is violated?"
  options={[
    { id: "monotonic", text: "Monotonic reads", correct: true, feedback: "Right. After observing version 7, the session went back in time to version 5. Pin the session to a replica, or carry its highest seen position as a token." },
    { id: "ryw", text: "Read-your-writes", feedback: "This user wrote nothing, so read-your-writes has nothing to promise them." },
    { id: "monotonic-writes", text: "Monotonic writes", feedback: "Monotonic writes orders a session's own writes. This session only read." },
    { id: "linear-only", text: "Only linearizability; every weaker guarantee holds", feedback: "Going backwards within one session already breaks monotonic reads, which is weaker than linearizability and much cheaper to provide." }
  ]}
/>

</Step>

<Step id="causal" title="Causal consistency">

Causal consistency keeps cause before effect for every reader. The classic failure without it: Alice posts "I lost my job", then, after reading the replies, posts "Never mind, it was a joke, I got promoted." Bob's replica receives the second post first and he congratulates her on losing her job.

Causal consistency is attractive because it is close to the strongest model a store can provide while staying available on every side of a partition. Linearizability requires a side to stop answering; causal ordering only requires each replica to delay showing an update until it has shown the updates it depends on.

<Choice

  objective="identify-violation"
  prompt="Bob reads Alice's question, then posts an answer. Carol's replica shows Bob's answer but not Alice's question. Which is the weakest model this violates?"
  options={[
    { id: "causal", text: "Causal consistency", correct: true, feedback: "Right. Bob's answer causally depends on Alice's question because Bob read it first. Showing the effect without the cause is the defining causal violation." },
    { id: "eventual", text: "Eventual consistency", feedback: "Carol's replica may still converge and show both posts later, which is all eventual consistency asks." },
    { id: "ryw", text: "Read-your-writes", feedback: "Carol did not write either post, so read-your-writes does not apply to her session." },
    { id: "linear", text: "Linearizability is the weakest model violated", feedback: "Linearizability is violated too, but a weaker model is violated already: causal consistency forbids exactly this." }
  ]}
/>

</Step>

<Step id="eventual" title="How stale is eventual?">

Eventual consistency gives no bound at all, so you have to measure or model it. In a leaderless store the dial is quorum size: with N replicas, a write acknowledged by W and a read of R, overlap is guaranteed only when R + W > N. Below that, a read can land entirely on replicas the write has not reached yet. Bailis et al. formalised this as "probabilistically bounded staleness"; the simple case is a counting problem.

Select **read repair** in Script and watch an older replica catch up when the read repairs it. Then compare **quorum overlap** with **sloppy quorum and hinted handoff** (keep Sloppy quorum with spare replicas checked): a spare can acknowledge a write that a home-only read misses until handoff.

<Step id="choose" title="Choose the weakest safe model">

Strong models are not free: each step up adds round trips, refusals during partitions, or both. A good design picks per feature. Linearizability is for things where two observers acting on different answers causes harm: uniqueness, locks, leader election, account balances. Session guarantees cover "my own changes must show up". Most social and analytical reads tolerate eventual consistency.
