<Step id="lost-ack" title="The lost acknowledgement">

A client sends "charge $50". The payment service charges the card, commits, and sends the response. The response is lost: a load balancer drops the connection, or the client's own timeout fires a moment too early. From the client's side this looks exactly like a request that never arrived. If it retries, the customer pays twice.

This is not an exotic failure. Any system that retries on timeout, which is every robust system, delivers some requests more than once. Networks give you **at-most-once** (never retry, sometimes lose) or **at-least-once** (retry, sometimes duplicate). Exactly-once *delivery* is not on offer; exactly-once *effects* are something you build.

<Step id="natural" title="Some operations are already safe to repeat">

An operation is **idempotent** if doing it twice has the same effect as doing it once. "Set the shipping address to X", "delete order 42" and an HTTP PUT of a whole resource are naturally idempotent. "Add $50", "append a line", "send an email" and "increment a counter" are not; each repeat changes the world again.

You can often redesign an operation to be idempotent: replace "increment by 1" with "record vote from user U on post P" under a unique constraint, or "add $50" with "apply transfer T-9123" where the transfer ID is unique. When that is not possible, the server must remember what it has already done.

<Step id="keys" title="Idempotency keys">

For operations that are not naturally idempotent, the client generates a unique **idempotency key**, typically a random UUID, once per logical operation, and sends the same key on every retry. Stripe's API popularised this with an `Idempotency-Key` header, and the IETF is standardising the header.

On the server, the first request with a key does the work and stores the result under the key. Any later request with the same key gets the stored result back without doing the work again. Stripe also stores a fingerprint of the request parameters and rejects a reuse of the key with different parameters, which catches client bugs.

<Step id="atomic" title="The race that breaks naive dedup">

The tempting implementation is: check whether the key exists; if not, do the work; then store the key. Two retries that arrive close together both pass the check before either stores the key, and both do the work. A crash between "do the work" and "store the key" has the same effect on the next retry.

The check and the record must be one atomic step, and the record must commit together with the effect. Inside one database, a transaction with a unique constraint on the key does this. When the effect lives elsewhere, such as a call to a card network, store the key with a "started" state first, pass your own key to that external system, and design a recovery path for requests that crashed midway, as Brandur Leach's Postgres design does with recovery points.

<Step id="retention" title="How long to remember a key">

A key must be kept at least as long as a client might retry with it, including retries after the client itself crashes and resumes. Too short, and a late retry is treated as new. Stripe keeps keys for at least 24 hours. The storage cost is rate × retention × entry size, and the stored response often dominates the entry size.

Expiry is a correctness boundary, not a tuning knob: document it as part of the API contract, and reject retries older than the window if you can detect them.

<Step id="consumers" title="Consumers deduplicate too">

The same reasoning applies to message queues. Most brokers deliver at least once: a consumer processes a message, crashes before acknowledging it, and the broker redelivers. A consumer that applies effects must be idempotent, usually by recording the message ID in the same transaction as the effect. Kafka's "exactly-once semantics" is this idea applied inside Kafka: transactional writes and offsets commit together, but effects outside Kafka still need their own deduplication.
