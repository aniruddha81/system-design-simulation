<Step id="drift" title="Every clock is wrong, differently">

A server's clock is a quartz oscillator counted by the kernel. Oscillators run slightly fast or slow, specified in **parts per million**: 1 ppm is one microsecond of error per second, or about 86 ms per day. NTP corrects clocks periodically, usually by slewing (running slightly faster or slower) and sometimes by stepping, which can move the clock **backwards**.

Between corrections, two clocks drift apart. If each can drift ρ ppm in either direction, after T seconds they can disagree by 2ρT microseconds, before even counting the error of the synchronisation itself. Measure durations with a monotonic clock, never the wall clock.

<Step id="lww" title="Last-writer-wins silently loses writes">

Many stores resolve conflicting writes with **last-writer-wins** (LWW): keep the value with the larger timestamp. With wall-clock timestamps this discards data whenever clocks disagree by more than the gap between two writes. Node A's clock runs 100 ms fast. A writes "first" at its time 1,100. Node B, whose clock is accurate, reads that value and then writes "later" at its time 1,050. B's write happened after A's, but it carries a smaller timestamp, so LWW keeps "first" and drops B's update, without any error.

<Step id="lamport" title="Lamport clocks capture happens-before">

Lamport (1978) replaced physical time with the **happens-before** relation: a happens before b if they are on the same process in that order, if a sends a message that b receives, or by transitivity. Events with neither order are **concurrent**.

A Lamport clock is a counter per process with three rules:

1. Before each local event, increment the counter.
2. Stamp every message with the counter.
3. On receive, set the counter to max(local, message stamp) and then increment.

This guarantees that if a happens before b, then L(a) is less than L(b).

Select **lamport clock** in Script. Step through sends and receives and check that every receive advances beyond both the local counter and the message stamp.

<Step id="lamport-limits" title="What a Lamport timestamp cannot tell you">

The guarantee runs one way only. A smaller Lamport timestamp does not mean the event happened first; two concurrent events can have any timestamps. Ties are broken by process ID to give a **total order** consistent with causality, which is enough for things like Lamport's mutual exclusion algorithm, or ordering a replicated log. It is not enough to detect conflicts.

<Step id="vector" title="Vector clocks detect concurrency">

A **vector clock** keeps one counter per process. A process increments its own entry on each event, sends the whole vector, and on receive takes the element-wise maximum and then increments its own entry. Now the comparison is exact: V(a) ≤ V(b) in every entry, and different in at least one, if and only if a happened before b. If each vector is larger in some entry, the events are concurrent.

Dynamo used vector clocks to keep concurrent versions of an object as siblings for the application to merge, instead of silently dropping one. The cost is size: one entry per writer, so systems truncate or use dotted version vectors bounded by replicas rather than clients.

<Step id="hlc" title="Hybrid logical clocks">

Logical clocks capture causality but say nothing about real time, so you cannot ask "what was the state at 10:00?". Physical clocks give real time but break causality. A **hybrid logical clock** (Kulkarni et al., 2014) combines them: the timestamp is a pair (l, c), where l is the largest physical time the node has heard of and c is a small counter for events that share the same l.

On each event or receive, l becomes the maximum of the local physical clock, its previous l, and any incoming l; c increments if l did not change and resets to zero if it did; on a receive that adopts the sender's l, c continues from the sender's counter. The result respects happens-before like a Lamport clock, fits in a 64-bit timestamp, and never strays from physical time by more than the clock offset. CockroachDB uses HLC timestamps for its transactions.

<Step id="truetime" title="TrueTime: admit the uncertainty, then wait it out">

Google's Spanner took a different approach: instead of pretending to know the time, its TrueTime API returns an interval, TT.now() = [earliest, latest], guaranteed to contain true time. GPS receivers and atomic clocks in every data centre keep the half-width ε small; the paper reports ε moving between about 1 and 7 ms between synchronisations.

To make commit order match real time across the planet, a transaction picks its commit timestamp s = TT.now().latest and then performs **commit wait**: it does not make its writes visible until TT.now().earliest has passed s. That wait is about 2ε. Spanner pays a few milliseconds per write to get externally consistent transactions, which is why it invests so much in shrinking ε.
