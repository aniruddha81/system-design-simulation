<Step id="why-timeouts" title="Every remote call needs a timeout">

A remote call can fail in a way that never returns: the server is alive but stuck, the connection is half-open after a network change, a response packet was lost and the TCP retransmission timer backs off into minutes. Without a timeout, the caller waits forever, holding a thread, a connection and memory.

A timeout turns "unknown" into a decision. It does not tell you what happened on the other side; a timed-out request may have completed. That matters as soon as you retry, which is why the [idempotency lesson](/learn/distributed-systems/idempotency) follows this one.

<Step id="from-data" title="Set the timeout from the latency distribution">

A timeout is a bet on the latency distribution. Amazon's Builders' Library describes the usual starting point: pick an acceptable rate of false timeouts, say 0.1%, and set the timeout at that percentile of the dependency's healthy latency, here p99.9, plus a little padding. Then check it fits inside what your own caller will wait.

Both errors hurt. Too short, and healthy slow requests fail and get retried, adding load exactly when latency is rising. Too long, and a dead dependency ties up resources for the whole wait.

<Step id="too-long" title="What an overlong timeout holds hostage">

When a dependency hangs, every in-flight call to it sits waiting until the timeout. By Little's law, the number stuck equals the call rate times the time each call is held. A generous timeout on a busy path can exhaust a whole thread pool in seconds, and then the service fails every request, including ones that never touch the broken dependency. That is how one slow dependency cascades into a full outage.

<Step id="attempts" title="Retries must fit inside the deadline">

The caller has its own deadline. Every attempt, and every sleep between attempts, comes out of the same budget. A per-try timeout of 1 s with three attempts behind an API that the user abandons after 2 s means the third attempt is wasted work. Budget backwards: user deadline, then attempts × per-try timeout plus sleeps.

<Step id="deadline" title="Propagate the deadline, not a fixed timeout">

In a chain of calls, fixed per-hop timeouts do not compose. If the gateway gives up after 1 s but service A gives B a fresh 1 s timeout, B can keep working long after the user is gone. Worse, each hop's retries multiply under the same wasted budget.

The fix is **deadline propagation**: pass the absolute deadline, or the remaining time, with the request. gRPC does this natively; each server sees how much time is left and passes that on, minus what it has already spent and what it needs to respond. A server that receives a request whose deadline has already passed should reject it immediately instead of doing the work.

<Step id="expired-work" title="Stop work nobody is waiting for">

Google's SRE book singles out work for timed-out requests as a key ingredient of cascading failure. Under overload, queues grow, so requests spend longer waiting; more of them expire while queued; the server keeps executing them anyway and produces responses no one reads. Goodput falls while utilisation stays at 100%.
