<Step id="convergence" title="Merge rules that cannot disagree">

An available store lets replicas accept writes during a partition, so they diverge. The question is how they converge again without asking a human. Last-writer-wins throws data away. Keeping siblings, as Dynamo did, pushes the merge to application code. **Conflict-free replicated data types** (Shapiro et al., 2011) build the merge into the data type itself, so that any two replicas that have received the same updates are in the same state. That property is called **strong eventual consistency**.

For state-based CRDTs, the merge function must be **commutative** (merge(a, b) = merge(b, a)), **associative** (grouping does not matter) and **idempotent** (merge(a, a) = a). Then replicas can exchange state in any order, any number of times, over any gossip path, and still end up identical.

<Step id="counter" title="Counters: G-Counter and PN-Counter">

A shared counter is the simplest CRDT and shows the core trick. A **G-Counter** (grow-only) keeps one entry per replica. Each replica increments only its own entry. Merge takes the **maximum** of each entry, and the counter's value is the **sum** of the entries. Taking the max is commutative, associative and idempotent, so no increment is ever lost or double-counted.

A **PN-Counter** supports decrements by pairing two G-Counters, one for increments and one for decrements, with value = sum(P) − sum(N).

Keep Replication algorithm set to **CRDT counters, set and RGA** and select **counter messages reorder and duplicate** in Script. Compare the replicas as messages arrive out of order and twice. This player merges uniquely identified operations, so duplicate delivery does not count an increment again.

<Step id="sets" title="Sets: add, remove and who wins">

Sets are where merge semantics become a product decision. Alice removes "milk" from a shared list while Bob, offline, adds "milk" again. What should the merged list show?

- **Last-writer-wins set**: compare timestamps; whichever is later wins. Clock skew decides, and one user's intent silently vanishes.
- **OR-Set** (observed-remove): each add creates a unique tag; a remove deletes only the tags it has *observed*. Bob's concurrent add has a tag Alice never saw, so it survives. This is **add-wins**.

Dynamo's cart, which merged by union, could resurrect deleted items. The OR-Set gets the semantics right because it can tell "removed after I saw it" from "added concurrently".

With Replication algorithm set to **CRDT counters, set and RGA**, select **observed-remove add wins** in Script. Watch the remove discard the observed add while the concurrent fresh add survives.

<Step id="ot" title="Collaborative text: operational transformation">

Text editing is harder because positions shift. If Alice inserts at index 3 and Bob, concurrently, inserts at index 10, applying Bob's operation unchanged after Alice's lands it in the wrong place. **Operational transformation**, introduced by Ellis and Gibbs in 1989, rewrites each incoming operation against the concurrent operations already applied: Bob's index 10 becomes 10 plus the length of Alice's insert.

Correct transformation functions for every pair of operations are notoriously hard to get right without a central order. Production OT systems, including Google Docs and its predecessors, rely on a server that puts all operations into one sequence, which makes transformation tractable.

Set Replication algorithm to **OT with transformation** and select **concurrent insertion** in Script. Compare the server and client text after delivery, then repeat under **OT without transformation** to see why unchanged positions can diverge.

<Step id="sequence-crdt" title="Sequence CRDTs: give every character an identity">

Sequence CRDTs such as RGA, Logoot and the structures inside Yjs and Automerge avoid index arithmetic altogether. Every character gets a unique, permanent identifier, and an insert says "after character X" rather than "at index 10". Deletion leaves a **tombstone** so later inserts can still refer to the deleted character. Concurrent inserts at the same spot are ordered by a deterministic tie-break on their identifiers.

This works peer to peer with no central server, which is why the local-first movement favours it. The cost is metadata: identifiers and tombstones can make the document's internal state much larger than its visible text, and garbage collecting tombstones requires knowing that every replica has seen the deletion.

With Replication algorithm set to **CRDT counters, set and RGA**, select **concurrent RGA edits** in Script. Follow the concurrent deletion and insertion, then compare the text and tombstones after all messages arrive.
