<Step id="requirements" title="Separate the read flood from the transactional core">

A hotel booking service looks like two completely different systems glued together. Ninety-five percent or more of requests are travellers browsing cities, filtering dates, and refreshing hotel pages. The remaining slice is checkout — where two guests clicking **Book** on the last Deluxe King room for New Year's Eve must never both win.

**Functional**: search room availability and nightly rates for a hotel across a `[checkIn, checkOut)` date range; place a time-bounded reservation hold while collecting payment; confirm or cancel a reservation and return inventory to the pool.

**Non-functional**: browse p99 under ~150 ms with high availability (eventual consistency of a few seconds is fine); checkout p99 under ~500 ms with **strict serializability per room-night counter** (zero unplanned overselling) and **idempotent retries** so a dropped mobile connection never books or charges a guest twice.

<Step id="estimates" title="Size the inventory and the traffic">

Suppose the platform lists **5 million hotels**, each averaging **5 room types**, bookable **365 days** ahead, with **4 million bookings per day**.

- **Inventory rows**: 5M × 5 × 365 ≈ **9.1 billion rows**. At ~64 bytes per row (`hotelId`, `roomTypeId`, `date`, `available`, `priceCents`, `version`), the entire global inventory is **~580 GB** — small enough to fit in a handful of sharded relational database nodes.
- **Booking writes**: 4M ÷ 86,400 s ≈ **46 bookings/s** average, or **~250 bookings/s** at a 5× peak. Even if each booking updates 3 nights, ~750 row updates/s is effortless for SQL.
- **Availability reads**: at a 100:1 browse-to-book ratio, peak search traffic is **~25,000 reads/s**. A short-TTL availability cache (10–15 s) absorbs 90%+ of these reads so the transactional database is saved for checkouts and cache misses.

<Step id="api" title="Design an idempotent booking API">

- `GET /v1/hotels/{hotelId}/availability?checkIn=2026-12-29&checkOut=2027-01-01` → **200** `{ roomTypes: [{ roomTypeId, available, priceCents }] }`. Served via cache-aside with a 15 s TTL.
- `POST /v1/reservations` with header `Idempotency-Key: <client-uuid>` and body `{ hotelId, roomTypeId, checkIn, checkOut, guestId }` → **201** `{ reservationId, status, expiresAt }` if inventory is claimed, or **409 Conflict** if any night in the range has zero availability.
- `DELETE /v1/reservations/{reservationId}` → **200** `{ status: "CANCELLED" }` after atomically transitioning status and incrementing `available` for each night.

<Step id="data-model" title="Model per-night inventory counters">

Instead of checking overlapping `[checkIn, checkOut)` intervals across millions of existing reservations on every checkout, maintain an explicit `inventory` counter row for each `(hotelId, roomTypeId, date)`:

- **`inventory`**: primary key `(hotelId, roomTypeId, date)`, columns `available INT NOT NULL`, `priceCents INT`.
- **`reservations`**: primary key `reservationId`, columns `hotelId`, `roomTypeId`, `checkIn`, `checkOut`, `guestId`, `status` (`HOLD | CONFIRMED | CANCELLED | EXPIRED`), `expiresAt`.

Shard both tables by `hotelId`. Because a reservation is always for a single hotel, every night of a stay lives on the **same shard**, so a multi-night booking is a single-shard local transaction — no distributed two-phase commit required!

<Step id="high-level" title="Put the read cache and transactional checkout together">

Clients hit a load balancer in front of stateless Booking API servers.
1. **Browse path**: API servers check the **Availability Cache** (`cacheAside`). On a miss, they query the `inventory` rows for the hotel in the **Booking DB** and populate the cache with a short TTL.
2. **Checkout path**: API servers check the **Idempotency Store** (`dedup`). On a new key, they execute an atomic conditional decrement (`decrementIfPositive` on `available`) for every night in the stay and insert the `reservations` record in the **Booking DB** (replicated semi-synchronously with leader fencing).

<Step id="deep-dive" title="Deep dive: holds, payment sagas, and overbooking">

### Never call a payment gateway inside a database lock
External card processors take 300–2,000 ms and occasionally hang. If you hold a row lock on `inventory` during the payment HTTP call, one slow payment freezes checkout for the entire hotel. Instead, split checkout into two short transactions:
1. **Acquire hold**: in a 3 ms DB transaction, atomically decrement `available` and insert `reservations(status='HOLD', expiresAt=now+10m)`.
2. **Charge card**: call the payment service outside any DB transaction, passing `reservationId` as the payment idempotency key.
3. **Confirm or release**: if payment succeeds, run `UPDATE reservations SET status='CONFIRMED' WHERE reservation_id=? AND status='HOLD'`. If payment fails or `expiresAt` passes, a background reaper transitions `HOLD → EXPIRED` and increments `available` back.

### Intentional overbooking
Hotels routinely sell 105% of physical capacity to account for no-shows. Model this explicitly in data (`available = physicalCapacity + overbookingAllowance - booked`) rather than loosening transaction isolation — you still want an exact, race-free ceiling.

<Step id="alternatives" title="Compare alternative concurrency designs">

- **Read-then-write in application code** (`SELECT available` → if `> 0` → `UPDATE available = available - 1`): under the `hot-hotel` flash-sale scenario in the simulator, concurrent requests read the same positive count before any write commits, driving `available` negative (`oversell`).
- **No availability cache**: every search page hits the transactional database. In the simulator, removing `availcache` saturates the database worker pool and drops goodput below 85%.
- **Optimistic concurrency (`WHERE version = :oldVersion`)**: avoids row locks during read-modify-write, but under a 50-user flash sale for a hotel with 20 rooms left, 49 of the 50 concurrent transactions abort on version mismatch and must retry, whereas `SET available = available - 1 WHERE available > 0` lets the database serialise and succeed all 20 valid bookings in one round trip.

<Step id="failures" title="Run the failure scenarios">

Test the reference design against three failure scenarios:

1. **Conference hotel flash sale (`hot-hotel`)**: 25% of all traffic targets one room type with only 2 rooms left. The cache absorbs the search spike, the first 2 bookings succeed, and every subsequent booking cleanly receives `409 Conflict` with zero `oversell` violations.
2. **Availability cache flush (`cache-flush`)**: `availcache` restarts empty at t = 1.5 s. Request coalescing collapses concurrent misses for the same hotel into a single DB query, refilling the cache without dropping requests.
3. **Database leader failover (`db-failover`)**: `bookingdb` crashes at t = 1.5 s. Cached searches (96% of traffic) continue working uninterrupted while a replica is promoted in ~0.5 s; semi-synchronous replication and fencing guarantee no confirmed reservation is lost.

<Step id="wrap-up" title="Wrap up and score your design">

When wrapping up a booking interview, highlight three operational safeguards:
- **Reconciliation**: a periodic audit query checks that `physicalCapacity + overbookingAllowance - available == COUNT(active HOLD + CONFIRMED reservations)` for every `(hotelId, roomTypeId, date)` row.
- **Cache invalidation on zero**: while a 15 s TTL is fine when 8 rooms remain, actively delete or update the cached hotel entry when `available` hits `0` so users stop clicking into a sold-out checkout funnel.
- **Bot & flash-sale protection**: rate-limit holds per account so a scraper cannot lock up an entire hotel with unpaid 10-minute holds.
