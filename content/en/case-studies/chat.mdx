<Step id="requirements" title="Requirements">

One-to-one and group messaging (up to a few hundred members). Deliver in real time to online devices; store and deliver later to offline devices, with a push notification. **Per-conversation order**, sent/delivered/read receipts, history.

Non-functional: delivery under ~200 ms p99 between online users in a region; **no message lost once the sender sees "sent", and none shown twice**; hundreds of millions of concurrent connections.

<Step id="estimates" title="Estimates">

- **Messages**: 500M daily users × 40 messages ÷ 86,400 ≈ **230k/s**, about 500k/s at peak.
- **Storage**: 20B messages/day × ~200 B ≈ **4 TB/day**, about 1.5 PB/year before replication, if the server keeps history.
- **Connections**: 200M concurrent devices ÷ ~1M connections per tuned gateway host ≈ **200–400 gateways**. Memory per idle connection, not CPU, is the limit.
- **Groups**: with an average of 20 members, delivery work is several times the send rate.

<Step id="api" title="API">

- Over the WebSocket, the client sends a message with `conversationId`, `messageId` and `body`. **The client generates the message ID** (a UUID) and reuses it on every retry. The server acks with the server sequence number once the message is durably stored.
- The server pushes messages with their `serverSeq`; the client acks delivery, which produces the "delivered" receipt.
- `GET /v1/conversations/{id}/messages?before=seq` pages through history by sequence number.

<Step id="data-model" title="Data model">

- **messages**: partition key `conversationId`, clustering key `serverSeq`. A history read is one partition range read — the layout Discord describes for Cassandra.
- **inbox**: per-user pending deliveries for offline devices, deleted once acknowledged.
- **dedup**: one record per (sender, messageId) with a TTL of about a day.

<Step id="high-level" title="High-level design">

Devices hold a WebSocket to a **connection gateway**. The gateway calls the **chat service**, which checks the dedup store, appends the message to the conversation's partition, publishes it to a **delivery log partitioned by conversation**, and acks. **Delivery workers** consume the log in order and push to the recipients' gateways, or write to the inbox and send a push notification for offline devices.

<Step id="deep-dive" title="Deep dive: ordering and exactly-once for people">

Networks give at-least-once at best. The client retries until acked; the server's dedup table turns repeats into success without re-storing; the recipient's client dedups deliveries by message ID. Together that **looks** exactly-once to people.

Global order is unnecessary and expensive. Order **within a conversation** is required: the chat service assigns a per-conversation sequence when it stores the message, and the delivery log is partitioned by conversation, so a consumer sees each conversation's messages in sequence. Clients display by sequence number and fill gaps from history.

<Step id="alternatives" title="Alternatives">

- **No idempotency key.** Run the lost-acknowledgement scenario against it: retried sends are stored twice and the engine reports a duplicated effect.
- **Polling.** Simple HTTP, but 200M devices polling every 5 s is 40M mostly empty requests a second, and latency equals the poll interval.
- **A relational store for messages.** Fine at millions of messages a day; at billions, the append-only, partition-local pattern suits a wide-column store, which is why Discord moved to Cassandra and later ScyllaDB.

<Step id="failures" title="Failure scenarios you can run">

- **Lost acknowledgements.** For 80 ms every response from the chat service to one gateway is dropped. The messages were stored; the gateway retries with the same ID and the dedup store answers "sent" without storing again. Most senders see a short delay.
- **Delivery workers crash** for half a second. Sending keeps working because it ends at the durable log; delivery pauses, then catches up. Redelivered messages stay in order because each conversation's partition is consumed in order.
- **A slow message store** (8× slower). Some sends exceed the gateway timeout and are retried; dedup keeps retries harmless, but they add load to a store that is already slow — retries need a budget.

<Step id="wrap-up" title="Wrap up">

Summarise: gateways holding connections, idempotent sends with client message IDs, messages partitioned by conversation with server sequence numbers, a partitioned delivery log, inboxes and push for offline devices. Risks: reconnect storms after a gateway failure (clients must reconnect with jittered backoff), huge-group hot partitions, retry budgets during store slowdowns. Then score each stage from 1 to 4.
