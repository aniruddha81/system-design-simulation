<Step id="requirements" title="Pin down what you are building">

A URL shortener maps a long URL to a short code and redirects every click. It sounds trivial, which is why interviewers use it: the interesting parts only appear once you ask the right questions.

**Functional**: create a code for a long URL (optionally a custom alias and an expiry), redirect `GET /{code}`, return 404 for unknown and 410 for expired codes, and let owners list and delete their links.

**Non-functional**: redirects sit in front of every click, so they need a p99 under about 50 ms at the server and 99.99% availability. Creation can tolerate brief outages. A code must never map to two URLs, codes should not be trivially enumerable, and links must survive at least five years.

<Step id="estimates" title="Work out the numbers">

Assume **100M new links a day** and **100 clicks per link**.

- **Writes**: 100M ÷ 86,400 s ≈ **1,160/s**, about 2,300/s at a 2× peak.
- **Reads**: 100 × 1,160 ≈ **116k redirects/s**, about 230k/s at peak.
- **Records**: 100M × 365 × 5 years ≈ **183 billion** links.
- **Storage**: 183B × ~500 B ≈ **91 TB**, about 275 TB with three replicas.
- **Code length**: 62⁶ ≈ 5.7 × 10¹⁰ is too few; 62⁷ ≈ 3.5 × 10¹² gives about 19× headroom. **Seven characters.**
- **Cache**: if about 1B distinct links are read per day and the hottest 20% take about 80% of clicks, caching 200M entries × 500 B ≈ **100 GB** — a handful of cache nodes.
- **Egress**: 116k/s × 500 B ≈ 58 MB/s. Bandwidth is not the constraint.

<Step id="api" title="Design the API">

- `POST /v1/urls` with `longUrl`, optional `customAlias` and `expiresAt`, and an `Idempotency-Key` header → **201** with the code; **409** if the alias is taken; **429** over quota.
- `GET /{code}` → **301 or 302** with a `Location` header; **404** unknown; **410** expired.
- `DELETE /v1/urls/{code}` (owner only) → **204**. Deleting must also delete the cached entry.

A **301** is permanent: browsers and proxies may cache it, so repeat clicks never reach you. That saves load but loses click analytics and makes deletion unreliable. A **302** (or 307) sends every click to you. If analytics is the product, use 302.

<Step id="data-model" title="Model the data">

One table, keyed and sharded by `code`: `code`, `longUrl`, `userId`, `createdAt`, `expiresAt`. Every redirect is a point lookup on the shard key, so nothing fans out. A secondary index on `userId` serves "my links" — rare, and the only non-key access path.

There are no joins and no multi-row transactions, so a key-value store fits as well as SQL. The trade-off: in a KV store you maintain the per-user index yourself, and alias uniqueness becomes a conditional write instead of a UNIQUE constraint.

<Step id="high-level" title="Draw the high-level design">

Clients reach a load balancer in front of stateless API servers. Redirects use **cache-aside**: check the cache, and on a miss read the store and fill the cache. Creation writes the store directly. The store is a leader with replicas, semi-synchronous so an acknowledged link survives a leader failure, with fencing so an old leader cannot accept writes after failover.

The cache is what carries the read load. In the simulated cell, 3,000 requests/s meet a store that can do about 2,700 reads/s: without the cache it saturates, with it the store runs at about a third of capacity.

<Step id="deep-dive" title="Deep dive: generating codes">

Three workable schemes:

1. **Counter + base 62.** Give each API server a range of IDs (Flickr's ticket servers, or Snowflake-style timestamp + worker + sequence IDs), so there is no per-request coordination and no collision by construction. Sequential codes are enumerable, so pass the counter through a keyed bijective permutation before encoding.
2. **Random 7 characters + insert-if-absent.** With n codes used out of N = 62⁷, the next insert collides with probability n ÷ N — about 5% when 183B are used. Retry on 409.
3. **Hash and truncate** (MD5 or SHA-256 of the URL). It collides like random codes, and it also couples codes to URLs: two users shortening the same URL share a code, its analytics and its deletion.

Custom aliases always need the insert-if-absent path, whatever scheme you pick for generated codes.

<Step id="alternatives" title="Alternatives and their trade-offs">

- **Key-value store instead of SQL.** Every access is by key, so a Dynamo-style store (N = 3, R = W = 2) scales writes horizontally without a resharding project. You lose the cheap owner index.
- **No cache.** Simpler and always fresh, but the store must take the full read rate. In the simulator the no-cache variant saturates the store and most redirects miss their deadline.
- **Hash truncation.** Free deduplication, but collisions and shared ownership.

<Step id="failures" title="Failure scenarios you can run">

The reference design runs in the simulator against three scenarios:

- **The cache restarts empty.** Every redirect misses until the hot set refills. Coalescing and the skewed popularity refill it within a few hundred milliseconds; the cost is a tail-latency spike.
- **One link goes viral** (30% of all clicks). The viral link costs one store read — it lives in the cache. The store gets busier from the long tail, not from the hot key.
- **The store's leader dies.** Detection takes three missed 100 ms heartbeats plus a 200 ms election. Cache hits keep redirecting through the outage; misses and new links fail for about half a second. Semi-synchronous replication and fencing mean no acknowledged link is lost.
