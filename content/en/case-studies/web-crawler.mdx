<Step id="requirements" title="Pin down what you are building">

A web crawler starts from a set of seed URLs, downloads pages, extracts outgoing links, and repeats across billions of pages. The challenge is not making HTTP requests — it is fetching at **6,000+ pages per second** without ever overloading a small web server, getting stuck in an infinite calendar trap, or wasting storage on duplicate pages.

**Functional**: ingest seed URLs, fetch HTML, parse outgoing links, canonicalise and deduplicate URLs, deduplicate near-identical page content, obey `robots.txt` (`Disallow` and `Crawl-delay`), and prioritise high-value or frequently changing pages for recrawl.

**Non-functional**: sustain ~15 billion pages per month (~5,800 pages/s average, ~12,000/s peak), guarantee strict **per-host politeness** (at most one in-flight request per host with a minimum delay between fetches), and survive worker crashes without losing the crawl frontier.

<Step id="estimates" title="Work out the numbers">

Assume **15 billion pages per month** and **100 KB average compressed HTML per page**:

- **Crawl rate**: 15B ÷ (30 × 86,400 s) ≈ **5,800 pages/s** average, ~12,000 pages/s at peak.
- **Ingress bandwidth**: 5,800/s × 100 KB ≈ **580 MB/s (4.6 Gbit/s)** sustained, ~10 Gbit/s peak.
- **Raw HTML storage**: 15B × 100 KB ≈ **1.5 PB** per crawl cycle in object storage.
- **URL deduplication volume**: if each page has ~80 outgoing links, parsers check ~460,000 URLs/s against the seen-URL filter.
- **Bloom filter memory**: 15B URLs × ~14.4 bits/URL (for a 0.1% false-positive rate) ≈ **27 GB of RAM** — fits across a handful of nodes.
- **Fetcher concurrency**: by Little's law, 6,000 pages/s × 0.5 s mean response time = **3,000 fetches in flight**.

<Step id="api" title="Design the internal interfaces">

A crawler is an internal pipeline, so its APIs connect the parser, frontier scheduler, and politeness caches:

- `POST /v1/frontier/urls` — parser workers submit batches of discovered `{ rawUrl, sourceHost, depth }`; the scheduler canonicalises each URL, checks the seen filter, and enqueues unseen URLs into the frontier.
- `GET /v1/robots/{domain}` — returns the parsed `Disallow` prefixes and `Crawl-delay` for a host, cached for up to 24 hours.
- `POST /v1/frontier/lease` — fetcher workers lease the next ready batch of URLs for hosts whose politeness timer has expired and acknowledge completion (`200`) once the HTML blob and metadata are stored.

<Step id="data-model" title="Model the data">

- **urlseen (Bloom filter + KV store)**: tracks canonicalised URLs that have already been enqueued so cycles in the web graph do not cause infinite recrawls.
- **robotsRules**: keyed by `domainId`, storing parsed robots directives and expiration timestamps.
- **pages**: keyed by `urlId`, storing `domain`, HTTP `status`, `crawledAt`, and a 64-bit `contentHash` (SimHash) indexed to detect near-duplicate pages.
- **htmlBlobs**: compressed raw HTML in an immutable object store, separate from the fast metadata store.

<Step id="high-level" title="Draw the high-level architecture">

Followed links flow through a clean loop:

1. **Frontier schedulers** canonicalise incoming URLs and check the **URL seen filter**.
2. Unseen URLs enter the **Politeness frontier queues**.
3. **Fetcher + parser workers** pull ready URLs, verify cached `robots.txt` rules, download the page, write the raw HTML to the **object store** and metadata/SimHash to the **metadata KV store**, and feed newly extracted links back to the scheduler.

<Step id="deep-dive" title="Deep dive: Mercator frontier, Bloom filters, and SimHash">

### 1. The Mercator two-tier frontier
A crawler needs both **prioritisation** (fetch high-PageRank news homepages before obscure forum archives) and **politeness** (never send concurrent requests to the same host). Mercator solves this with two tiers of queues:
- **Front queues (`F_1 .. F_k`)**: `k` priority levels. A classifier assigns each URL to a priority queue based on domain authority and change frequency.
- **Back queues (`B_1 .. B_n`)**: each active host maps to exactly one back FIFO queue. A min-heap tracks the earliest next fetch time `t_next` for each host; when a worker pops the heap root, it fetches one URL from that host's back queue and re-inserts the host at `t_now + crawlDelay`.

### 3. Content deduplication with SimHash
Different URLs often serve identical or near-identical text (`example.com/item?ref=a` vs `example.com/print/item`). Cryptographic hashes like SHA-256 change completely if a single timestamp or ad banner changes. **SimHash** hashes each word/shingle into a 64-bit vector, weights bits by term weight, and collapses the sign of each position into a 64-bit fingerprint. Two pages are near-duplicates if the Hamming distance between their 64-bit fingerprints is at most $d = 3$.

<Step id="alternatives" title="Evaluate alternatives">

- **No `robots.txt` cache (hit the store on every check)**: in the simulator, removing the in-memory `robotscache` forces every check to scan/read the metadata store, saturating it and dropping goodput below 90%.
- **Database lookup instead of a Bloom filter for URL dedup**: checking 460k outgoing links/s against disk-backed indexes requires a massive database cluster; an in-memory Bloom filter rejects 99.9% of duplicates in nanoseconds.
- **Consistent host-to-worker hashing**: pinning each hostname to one fetcher partition via consistent hashing ensures both the host's back queue and its connection pool stay local to one worker.

<Step id="failures" title="Run the failure scenarios">

Test the reference design against three failure modes in the simulator:

- **Link discovery burst (`link-burst`)**: crawlers hit directory/sitemap hub pages and traffic doubles. The URL dedup store drops already-seen links and the frontier queue absorbs the burst so fetchers continue at a polite pace.
- **Fetcher worker crash (`fetcher-crash`)**: fetcher workers die for 500 ms while holding leased URLs. Because frontier leases use a visibility timeout, unacknowledged URLs become visible again and are fetched cleanly on recovery.
- **Slow archive object store (`slow-archive`)**: writing compressed HTML blobs degrades 4×. Because fetching happens asynchronously behind the frontier queue, scheduling and robots lookups stay fast.

<Step id="wrap-up" title="Wrap up and self-assess">

Close your design by addressing **spider traps** — dynamic pages like infinite calendars (`/calendar/2099/12/31`), session IDs in URLs, or faceted filters that generate billions of useless URLs. Defend against them with:
1. Strict URL canonicalisation and maximum URL length / path depth caps.
2. Per-host crawl budgets (maximum pages fetched per domain per cycle).
3. Monitoring repeat SimHash rates per host (if a host produces 10,000 URLs with near-identical SimHashes, demote its priority).
