<Step id="requirements" title="Requirements">

get, set with TTL, and delete for keys up to 250 B and values up to 1 MB, used cache-aside by many services. Sub-millisecond p99. The requirement that drives everything: **the hit rate must stay high enough that the database never sees more than its capacity** — including right after a cache node restarts.

<Step id="estimates" title="Estimates">

- **Load**: 1M reads/s at peak; the database can take ~50k reads/s, so the hit rate must stay **≥ 95%**.
- **Working set**: 100M objects × ~1 KB ≈ 100 GB.
- **Nodes**: 100 GB ÷ ~25 GB usable per node = 4 by memory; 1M ops/s ÷ ~200k per node = 5 by throughput. **Plan 8.**
- **Losing one of 8 nodes**: an eighth of the keys miss at once, about **125k extra reads/s** — 2.5× the database's capacity unless misses are coalesced or the node is replaced warm.

<Step id="api" title="API">

`get(key)` returns the value or a miss; `set(key, value, ttl)` stores with a TTL that has random jitter, so keys written together do not expire together; `delete(key)` is what writers call after committing to the database. Keys are namespaced and versioned, such as `profile:v3:{id}`, so a schema change invalidates everything by changing the prefix.

<Step id="data-model" title="Partitioning the keys">

Clients, or a proxy such as mcrouter or twemproxy, map each key to a node with **consistent hashing**: adding or removing one of n nodes remaps about 1/n of the keys, where hash mod n remaps almost all of them and empties the whole cache at once. Redis Cluster uses 16,384 fixed hash slots assigned to nodes — a directory variant of the same idea.

<Step id="high-level" title="High-level design">

Application servers run cache-aside: get from the cache; on a miss read the database and set the value. Writers update the database and then **delete** the key. The cache tier has many nodes partitioned by consistent hashing, possibly behind a proxy layer that handles routing, connection pooling and replication of hot keys.

<Step id="deep-dive" title="Deep dive: races, leases and hot keys">

Cache-aside has a classic race: a reader misses and reads v1; a writer commits v2 and deletes the key; the reader then sets **v1**, which stays until TTL. Facebook's memcache paper fixes it with **leases**: a miss returns a token, a delete invalidates outstanding tokens, and a set with an invalid token is ignored. Leases also throttle the stampede, because only the token holder fills a key.

**Hot keys** can exceed one node's capacity. Replicate them under several names and read a random one, keep a small in-process cache with a TTL of a second or two, or detect and pin them to dedicated replicas.

<Step id="alternatives" title="Alternatives">

- **No request coalescing.** In the simulated cell, with ~4 ms fills, it changes surprisingly little: most post-restart misses are distinct long-tail keys. Coalescing pays when one key is very hot relative to fill time — overlapping misses ≈ that key's request rate × fill time.
- **Write-through (update on write).** Reads after writes hit at once, but concurrent writers can leave the older value cached.
- **Replicated cache** (every node holds every key). No misses on node loss and perfect hot-key spreading, but capacity is one node's memory. Good for small, very hot data such as configuration.

<Step id="failures" title="Failure scenarios you can run">

- **Cold restart.** Hit rate drops to zero and the 8-worker database gets everything for a moment; the hot set refills within a few hundred milliseconds and only the tail pays.
- **Restart while the database is slow** (a migration is running). The cold cache sends the database four times what it can serve; rejected reads never fill the cache, so the cache stays cold and the database stays overloaded — a **metastable failure** that does not recover by itself.
- **A slow cache** (8 ms against a 5 ms timeout). Every read pays the timeout, then goes to the database: a slow cache is worse than a dead one.
- **Writes triple on popular keys.** Invalidations knock hot keys out over and over; the database runs near saturation.

<Step id="wrap-up" title="Wrap up">

Summarise: consistent-hash partitioning, cache-aside with delete-on-write and leases, TTL jitter, coalescing, hot-key replication, gutter pools and warm-up for node loss. Size the database for the **worst plausible hit rate**, not the average. Signals: hit rate per node, database headroom, and eviction rate. Then score each stage from 1 to 4.
