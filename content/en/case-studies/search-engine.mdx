<Step id="requirements" title="Pin down what you are building">

A full-text search engine ingests billions of documents, builds an **inverted index** mapping every term to the documents containing it, and answers multi-word queries with ranked results and highlighted snippets in under **200 ms**.

**Functional**: full-text boolean, phrase, and ranked keyword search; multi-stage ranking combining lexical match (**BM25**), static document quality (**PageRank**), and learned re-ranking; dynamic snippet generation; continuous near-real-time document indexing.

**Non-functional**: p99 latency < 200–250 ms across puluhan shards; high availability (gracefully return partial results from responding shards if one shard lags); scale to ~20B documents and ~100k queries/s.

<Step id="estimates" title="Work out the numbers">

Assume **20 billion documents**, **200 unique terms per document**, and **8 billion queries per day**:

- **Query rate**: 8B ÷ 86,400 s ≈ **93,000 queries/s** average, ~200,000/s peak.
- **Postings count**: 20B docs × 200 unique terms = **4 trillion postings**.
- **Compressed inverted index size**: storing sorted `docId` gaps (`delta = docId[i] - docId[i-1]`), term frequencies, and positions with block bit-packing (~8 bytes per posting) ≈ **32 TB** total. Across 64 shards, each shard holds **~500 GB** — fitting comfortably in RAM + fast NVMe per shard replica.
- **Tail amplification**: if each of 64 independent shards has a 99th-percentile latency of 50 ms (`P(fast) = 0.99`), the probability that **all 64** finish under 50 ms is `0.99⁶⁴ ≈ 0.526` (`52.6%`).
Nearly **half** of all uncached queries experience at least one 99th-percentile shard!

<Step id="data-model" title="Model the inverted index and sharding strategy">

An **inverted index** stores a dictionary of terms, where each term points to a sorted **postings list**:

`term → [(docId_1, tf_1, pos_1), (docId_2, tf_2, pos_2), ...]`

How should we shard this index across 64 machines?

1. **Document partitioning (local index per shard)**: hash each document `docId` to one of 64 shards. Each shard builds a complete inverted index for its 1/64th slice of documents.
2. **Term partitioning (global index per term)**: hash each `term` to one shard (`"apple"` on shard 1, `"banana"` on shard 2).

Production web search engines use **document partitioning** because a multi-word query (`"system design interview"`) can intersect the postings lists for all three words **locally in memory on each shard**, whereas term partitioning would require shipping gigabytes of postings lists across the network to intersect common words.

<Step id="high-level" title="Draw the high-level architecture">

Look at the reference design in the simulator:

1. **Query coordinators** (`coord1`, `coord2`) check the **Query result cache** (`qcache`).
2. On a cache miss, the coordinator **scatters** the query in parallel (`parallel(all)`) across the **Inverted index shards** (`idx1`, `idx2`).
3. Each shard intersects its posting lists, scores top matches, and returns top `(docId, score)` candidates.
4. The coordinator merges the candidates, fetches the winning documents' snippets from the **Document store** (`docstore`), caches the response, and returns `200`.

<Step id="deep-dive" title="Deep dive: WAND pruning, immutable segments, and tail defences">

### 1. Fast postings intersection and WAND
When intersecting `"distributed"` (10M docs) and `"consensus"` (500k docs), we advance pointers through both `docId`-sorted lists using **skip pointers** (or galloping search) to jump over non-matching blocks in $O(\log N)$ steps. Better yet, **WAND (Weak AND)** and **Block-Max WAND** record the maximum possible BM25 score in each block of 128 postings; if the sum of upper bounds for a document cannot beat the current $k$-th best score in the min-heap, WAND skips scoring that document (and entire blocks) altogether.

### 2. Real-time indexing via immutable LSM segments
Mutating delta-compressed posting lists in place on disk is impossible without rewriting megabytes per word. Following **Apache Lucene**, new documents are buffered in memory and flushed every second as a new **immutable segment**. A search queries all active segments on the shard; background threads merge small segments into larger ones and purge deleted `docId`s.

### 3. Defending against the 64-shard tail
Because `P(all 64 fast)` is low, coordinators combine three techniques:
- **Query and posting caches**: popular queries hit `qcache` directly; common sub-clauses cache their intersected bitsets inside shards.
- **Hedged requests**: if shard 17 has not responded after 30 ms (its p95), send a duplicate request to shard 17's replica and take whichever answers first.
- **Soft timeouts (partial results)**: at 150 ms, merge and return the results from the 63 shards that answered rather than failing the user's search.

<Step id="alternatives" title="Evaluate alternatives">

- **No inverted index (`search-full-scan`)**: in the simulator, querying `docstore` without the inverted index scans all rows on every search, saturating the store and failing the latency SLO.
- **Tiered indexes (hot in-memory tier vs cold full tier)**: keep the top 10% highest-PageRank documents in an all-RAM tier searched on every query; only fall back to the 90% cold tier if the hot tier fails to find $k$ high-scoring matches.
- **Precomputed single-term top-k lists (fancy lists)**: store a short list of the top 1,000 highest-scoring documents for each term at the front of its posting list so single-term and high-authority queries terminate almost immediately.

<Step id="failures" title="Run the failure scenarios">

Run the three failure scenarios in the simulator:

- **One index shard degrades 6× (`slow-shard`)**: a heavy background segment merge slows down `idx2`. Because `parallel(all)` waits for both shards on every cache miss, p99 latency rises across uncached queries while cached queries stay fast.
- **Index shard outage (`shard-outage`)**: `idx2` goes down for 400 ms. Cache hits and document writes continue, while uncached searches fail until the shard recovers (or until a production coordinator falls back to a replica / partial results).
- **Viral news query (`hot-query`)**: 35% of searches ask for the same query. `qcache` absorbs the spike after the first scatter-gather.

<Step id="wrap-up" title="Wrap up and self-assess">

Review the architecture end to end:
- **Document-partitioned shards** keep multi-term intersection local in memory.
- **Block-Max WAND + delta compression** make local intersection fast and compact.
- **Two-phase scatter-gather** fetches snippets only for the final top 10.
- **Query caching, hedged replicas, and soft timeouts** tame the $1 - p^N$ fan-out tail.
