<Step id="requirements" title="Requirements">

Limit each client (API key, user or IP) to rules such as 100 requests a minute, with short bursts allowed. Rejected requests get **429 Too Many Requests** with `Retry-After`. Rules change without a deploy.

Non-functional: a check adds under 1 ms p99; limits hold across all API servers within a small tolerance; and — the requirement people forget — **the limiter failing must not take the API down**, so the failure policy is decided up front.

<Step id="estimates" title="Estimates">

- **Checks**: every request is checked — at 50k requests/s that is 50k counter operations/s.
- **State**: 1M active clients × 3 rules × ~50 B ≈ **150 MB**. Fits in memory on one Redis node.
- **Throughput**: ~100k simple operations/s per Redis shard, so one shard is enough; run three for headroom and blast radius.
- **Latency**: same-zone round trip ≈ 0.5 ms + operation ≈ 0.1 ms ≈ **0.6 ms**, inside the 1 ms budget.
- **The simulated cell**: two API servers × 16 workers ÷ ~10 ms per request ≈ 3,200 requests/s of capacity, protected by a global limit of 2,000/s with a 400-token burst.

<Step id="api" title="API and headers">

The limiter has no public API of its own; it shapes every response. Allowed requests pass through. Rejected ones get 429 with `Retry-After` and rate-limit headers (limit, remaining, reset) so well-behaved clients can pace themselves. Rules are managed by an internal API and pushed to limiters as configuration, cached locally.

<Step id="data-model" title="Counter state">

State is one small key per (client, rule), with a TTL slightly longer than the window so idle clients cost nothing:

- **Token bucket**: tokens and last refill time. Allows bursts of B and a sustained rate r.
- **Fixed window**: one counter per window. Cheap, but a client can send 2× the limit across a window boundary.
- **Sliding-window counter**: current and previous counts; the rolling estimate is current + previous × overlap fraction.

The update must be **atomic** — a Lua script or INCR with EXPIRE. A read followed by a write lets two servers read the same count and both allow.

<Step id="high-level" title="High-level design">

Requests pass the **API gateway** (authentication, size limits), then the **limiter** with shared counters, then the load balancer and API servers. Limiting at the gateway rejects excess work before any expensive processing happens.

Layer the protection: a coarse per-IP limit at the edge against floods, per-key quotas at the gateway, and concurrency limits inside services. A rate limit cannot see a slow dependency: at the same request rate, slower responses mean more requests in flight.

<Step id="deep-dive" title="Deep dive: making shared counters fast and safe">

A shared counter costs one round trip per request. To cut that, servers can take tokens locally **in chunks** and sync every few hundred milliseconds, accepting a small overshoot. Shard counters by client key so one hot client cannot overload every shard. Put a tight timeout on the counter call and decide what happens when it expires — for overload protection, **allow** and fall back to a local limit.

<Step id="alternatives" title="Alternatives">

- **No limiter.** Under a 6× burst the backend completes about as many requests as it can — roughly the same goodput in the simulator — but every request waits in a full queue: median latency rises about 10× and failures are slow timeouts instead of instant 429s.
- **Local in-process limiters.** No network hop and nothing shared to fail, but the effective limit is the per-server limit times the number of servers, and it drifts as the fleet scales.
- **Sliding window instead of token bucket.** The sliding-window counter fixes most of the fixed window's boundary burst; a token bucket expresses "sustained rate plus burst" directly.

<Step id="failures" title="Failure scenarios you can run">

- **A 6× burst.** The limiter admits about 2,000 requests/s and answers the rest with 429 in well under a millisecond. Admitted requests stay fast because the backend stays at about two-thirds utilisation.
- **A slow counter store** (50× slower checks). Every request pays it, because the limiter is in the path, even though nobody is over quota.
- **The limiter dies.** In this topology every request times out for the whole outage: a protection layer became a single point of failure.
