<Step id="requirements" title="Pin down what you are building">

A payment system (like Stripe, Adyen, or Square) accepts charge and refund requests from merchants, coordinates with external card networks / Payment Service Providers (PSPs), and maintains an authoritative financial ledger. When a network packet drops, **retrying a payment must never charge the customer twice**, and **no acknowledged payment may ever vanish**.

**Functional**: authorize, capture, and refund payments; maintain an **immutable double-entry ledger** (`SUM(debits) == SUM(credits)`) for every balance change; support client-supplied `Idempotency-Key`s; run daily T+1 reconciliation against external PSP settlement files.

**Non-functional**: zero duplicate charges (`duplicateEffect`); zero lost acknowledged transactions; store all amounts in **integer minor units** (`amountCents` + ISO currency, never floating point); full append-only audit trail.

<Step id="estimates" title="Work out the numbers">

Assume **500 million payments per day** (~5,800 TPS average, **~20,000 TPS** peak during flash sales):

- **Ledger postings**: each payment writes ~4 immutable ledger rows (debit buyer clearing, credit merchant payable, credit platform fee, settlement entry) $\Rightarrow$ **2 billion rows/day** × 200 B ≈ **400 GB/day** (~150 TB/year).
- **Idempotency key footprint**: 500M keys/day × 128 B ≈ **64 GB/day** — easily fits in an in-memory + transactional store with a 24–48 hour TTL.
- **External PSP latency**: card network rails take **200–1,000 ms** p99, whereas local database transactions take **2–5 ms**.
- **Crucial consequence**: if a database connection pool of 200 connections held a DB transaction open during a 500 ms PSP call, the entire database would cap out at `200 ÷ 0.5 s = 400 TPS`! Never hold DB locks across external network calls.

<Step id="api" title="Design the API">

Every state-changing endpoint requires an **`Idempotency-Key` header** generated by the caller (e.g. UUIDv4 tied to the checkout order ID):

- `POST /v1/payments` (`Idempotency-Key: <uuid>`, `{ amountCents, currency, merchantId, paymentMethod }`) → `200 { paymentId, status, ledgerTxId }`.
  - If the key was already completed, return the **stored response payload** without executing again.
  - If a first request with that key is currently `IN_PROGRESS`, return `409 Conflict` (or hold briefly until completion).
  - If the caller reuses the same key with a **different** `amountCents` or `merchantId`, reject with `422 Unprocessable Entity`.
- `POST /v1/payments/{id}/refunds` (`Idempotency-Key: <uuid>`, `{ amountCents }`) → appends compensating reversal entries.
- `GET /v1/payments/{id}` → `200 { paymentId, status, amountCents, entries[] }`.

<Step id="data-model" title="Model the double-entry ledger">

Never track money with a mutable `UPDATE accounts SET balance = balance + 1000` statement alone. Instead, model three core tables in your ACID database:

1. **`idempotency_keys`**: `(merchantId, idempotencyKey) PRIMARY KEY, requestHash, status, responseBody, createdAt`.
2. **`payments` (state machine)**: `paymentId, merchantId, amountCents, currency, status (CREATED → AUTHORIZED → CAPTURED → SETTLED | FAILED), version`.
3. **`ledger_entries` (append-only double-entry log)**: `entryId, txId, accountId, direction ('DEBIT' | 'CREDIT'), amountCents, createdAt`.

Every ledger transaction `txId` satisfies the zero-sum accounting invariant:

`SUM(amountCents WHERE direction = 'DEBIT') == SUM(amountCents WHERE direction = 'CREDIT')`

And if a charge is refunded, you **never** `DELETE` or `UPDATE` the original rows — you append a new compensating transaction with the opposite `DEBIT`/`CREDIT` directions.

<Step id="high-level" title="Draw the high-level architecture">

Look at the reference design in the simulator:

1. **Payment gateways** (`gw1`, `gw2`) terminate TLS, authenticate the merchant, and call the **Payment orchestrator** (`pay`) with a timeout and bounded retry policy (`backoff`).
2. `pay` executes an atomic check-and-record against the **Idempotency key store** (`idemp`).
3. If `dedupHit` is true, `pay` immediately returns `200` with the previously recorded result.
4. Otherwise, `pay` appends the double-entry rows to the **Double-entry ledger DB** (`ledgerdb`), publishes the settlement/capture job to the **Transactional outbox queue** (`outbox`), and returns `200`.
5. **PSP capture + reconciliation workers** (`settler`) consume `outbox` and update settlement state.

<Step id="deep-dive" title="Deep dive: 2PC vs Sagas, Outbox, and Hot Accounts">

### 1. Why Sagas + Transactional Outbox beat 2PC for external PSPs
You cannot run Two-Phase Commit (2PC) across your internal database and Visa/Mastercard's HTTP API — card networks do not expose a `PREPARE` lock endpoint, and coordinator crashes in 2PC leave participants blocked holding locks. Instead, use a **Saga** driven by a **Transactional Outbox**:
- Commit the ledger state transition and an `outbox` row in the **same local database transaction**.
- A worker relays the outbox event to the external PSP (passing a deterministic PSP idempotency key derived from `paymentId`).
- If a downstream step fails permanently, execute an explicit **compensating action** (void authorization or issue reversal ledger entries).

### 2. Sharding hot merchant accounts
If 5,000 customers per second buy from the same mega-merchant, updating a single `merchant_balance` row serialises all 5,000 transactions on one row lock! Because `ledger_entries` is **append-only**, inserts do not lock a single row; if you also enforce a real-time balance floor, split the hot account into $N = 16$ sub-accounts (`merchant#0` .. `merchant#15`) and route each credit to `merchant#(hash(paymentId) % 16)`.

<Step id="alternatives" title="Evaluate alternatives">

- **No idempotency store (`payment-no-dedup`)**: in the simulator, switch to the `payment-no-dedup` alternative and run the `lost-acks` scenario. When responses from `pay` to `gw1` are dropped, `gw1` retries and the engine flags a **`duplicateEffect` invariant violation** (double charge!).
- **Synchronous PSP call vs queued capture**: authorization typically happens synchronously while the user waits at checkout (still using the 3-step `IN_PROGRESS` $\rightarrow$ PSP call outside DB lock $\rightarrow$ `AUTHORIZED` pattern), while capture, settlement, and webhook delivery run asynchronously via the outbox queue.

<Step id="failures" title="Run the failure scenarios">

Run the three failure scenarios in the simulator:

- **Lost acknowledgements (`lost-acks`)**: from `t = 1.5 s` to `1.58 s`, responses on the `pay → gw1` link are dropped after `pay` has already committed to `ledgerdb`. Gateway 1 times out and retries with the same key. The reference design's `idemp` store catches every retry (`clean: true`, zero violations), whereas the `payment-no-dedup` alternative violates `duplicateEffect`.
- **Settlement worker crash (`settler-crash`)**: `settler` workers die for 600 ms. Charge acceptance stays above 99% goodput while outbox messages wait safely in `outbox`.
- **Ledger database leader failover (`ledger-failover`)**: `ledgerdb` fails over to a semi-sync replica with fencing. Writes fail closed during the 500 ms election and zero acknowledged writes are lost.

<Step id="wrap-up" title="Wrap up and self-assess">

Close with **T+1 settlement reconciliation** — the final safety net of every real payment system. Every night, external card networks and banks provide settlement batch files listing every captured transaction and fee. An automated reconciliation job joins that file against `ledger_entries`:
1. **In internal ledger, missing at PSP**: retry capture or void/reverse the pending ledger entry.
2. **Charged at PSP, missing in internal ledger**: an unrecorded side effect after a crash — append the missing ledger entry or trigger an automatic refund.
3. **Continuous invariant monitor**: verify `SUM(debits) == SUM(credits)` across every transaction and alert immediately on any discrepancy.
