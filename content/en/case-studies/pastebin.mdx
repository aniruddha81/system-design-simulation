<Step id="requirements" title="Requirements">

Users paste text (typically ~10 KB, up to 10 MB), get back an unguessable ID, and share the link. Pastes can expire (from ten minutes to never) or be **burn-after-read**. Signed-in users can list and delete their pastes.

Non-functional: reads p99 under 200 ms for typical pastes, 99.9% read availability, and an acknowledged paste is never lost. Because storage grows forever, **cost per GB** is a first-class requirement.

<Step id="estimates" title="Estimates">

Assume **10M new pastes a day** and **10 reads per paste**.

- **Writes**: 10M ÷ 86,400 ≈ **116/s**, about 230/s at peak. **Reads**: about 1,160/s, 2,300/s at peak.
- **Content**: 10M × 10 KB × 365 × 5 years ≈ **183 TB**. In an object store at $0.023/GB-month that is about $4k a month.
- **Metadata**: 18B rows × ~300 B ≈ **5.5 TB**.
- **Egress**: 2,300/s × 10 KB ≈ 23 MB/s at peak.
- **Cache**: the hottest 20% of a day's reads is 0.2 × 100M × 10 KB ≈ **200 GB**. Each entry is 20× bigger than a short link, so size the cache in **bytes**, not entries.

<Step id="api" title="API">

- `POST /v1/pastes` with `content`, `syntax`, `expiresIn`, `burnAfterRead` and an `Idempotency-Key` → **201** with the ID; **413** too large (rejected at the gateway before the body is read); **429** over quota.
- `GET /p/{id}` → **200** text; **404**; **410** expired.
- `DELETE /v1/pastes/{id}` → **204**: delete metadata, schedule the blob for deletion, invalidate caches.

IDs are random 8-character base-62 strings (about 2 × 10¹⁴ values), never counters: pastes often contain secrets, so IDs must not be enumerable.

<Step id="data-model" title="Data model: two stores">

- **pastes** (database): `id`, `userId`, `title`, `syntax`, `blobKey`, `createdAt`, `expiresAt`, with indexes on `userId` and `expiresAt`. Small rows that need indexes.
- **blobs** (object store): `blobKey → content`. Cheap per GB and designed for very high durability, but tens of milliseconds per read.

**Write order matters.** Write the blob first, then the metadata. A crash in between leaves an unreferenced blob that a sweeper deletes. The opposite order can leave a paste whose content does not exist — a 404 for a paste the user was told was saved.

<Step id="high-level" title="High-level design">

A load balancer spreads requests over stateless API servers. Reads go **cache → metadata → blob**: a hit returns the cached paste; a miss reads metadata, then the blob, then fills the cache. Pastes are immutable, so the cache never needs invalidating except on delete or expiry. Creates write the blob, then the metadata.

Blob reads retry with exponential backoff and jitter. That is safe because a read has no side effects. The blob write does not retry here: without an idempotency key, a retried create could store a second copy.

<Step id="deep-dive" title="Deep dive: expiry and burn-after-read">

**Expiry**: check `expiresAt` on every read and return 410, so expired pastes disappear immediately. A background job walks the `expiresAt` index in small batches and deletes metadata, then blobs. Object stores also offer lifecycle rules that delete by age, which removes most of the sweeper's work for fixed TTLs.

**Burn-after-read** needs an atomic read-and-delete — a conditional delete on the metadata row. With a separate read and delete, two readers who arrive together can both see the paste.

<Step id="alternatives" title="Alternatives">

- **Content in the database.** One system, one transaction, no orphans. Fine below a few TB; at 183 TB it means many more shards, slower backups and replicas that copy every byte.
- **A CDN for public pastes.** Immutable public pastes cache perfectly at the edge. Private and burn-after-read pastes must bypass it, and deletes need a purge.
- **No retries on blob reads.** Run the lossy-link scenario against it: every lost packet becomes a failed read, where the reference design's retries hide almost all of them.

<Step id="failures" title="Failure scenarios you can run">

- **The object store slows down 8×** (120 ms per read). Cache hits are untouched; misses slow down and API workers spend longer waiting, so their utilisation rises. A slow dependency consumes your concurrency even though it is not your CPU.
- **Packet loss between one API server and the object store** (10%). Blob reads retry with backoff and nearly all succeed; a few creates fail because they do not retry.
- **A paste goes viral** (40% of reads). It is served from the cache after the first read; the long tail is what keeps the object store busy.
