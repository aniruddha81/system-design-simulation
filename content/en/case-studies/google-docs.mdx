<Step id="requirements" title="Pin down what you are building">

A collaborative editor lets dozens of users type into the same document simultaneously, apply local keystrokes with **zero perceived latency**, and converge to the **exact same document text** once all operations arrive.

**Functional**: real-time concurrent text editing; live collaborator cursors and selections; offline edits that merge cleanly on reconnect; version history and point-in-time document restore.

**Non-functional**: optimistic local typing (0 ms UI wait) with remote propagation under ~150 ms; **strong eventual convergence**; zero lost or duplicated operations across flaky WebSocket reconnects; cap active concurrent writers per document at ~100 while scaling read-only viewers to thousands.

<Step id="estimates" title="Work out the numbers">

Assume **5 million concurrent active editors** who send a batched operation every **2 seconds**:

- **Operation write rate**: 5M ÷ 2 s ≈ **2.5 million ops/s** globally (~150 B per op).
- **Operation log growth**: 2.5M/s × 150 B × 86,400 s ≈ **32 TB/day** of raw operations before compaction.
- **Snapshot compaction**: compacting every ~100–500 operations into a materialised snapshot (~50 KB) in object storage bounds document load time to **1 snapshot read + < 100 tail ops**.
- **Cursor broadcast fan-out**: $K$ editors in one document moving cursors 5 times/s generate $5 \times K^2$ messages/s ($K = 50 \Rightarrow 12,500$ messages/s per hot doc). Because cursor positions are obsolete 200 ms later, they are broadcast in memory over WebSockets and **never written to disk**.

<Step id="api" title="Design the protocol and API">

- `WS op { docId, opId, baseRev, delta }` → server transforms `delta` against any operations committed since `baseRev`, appends it as `serverRev`, replies `ack { opId, serverRev }` to the sender, and broadcasts `{ serverRev, author, transformedDelta }` to all other session peers.
- `GET /v1/documents/{docId}` → `200 { snapshotRev, snapshotContent, tailOps[] }` (where `tailOps` are operations with `rev > snapshotRev`).
- `WS presence { docId, cursor, selection }` → best-effort broadcast to connected peers.

In **Jupiter-style OT** (used by Google Docs), each client keeps **at most one unacknowledged operation batch in flight** to the server while buffering newer local keystrokes, simplifying transformation to a 1D server-revision history instead of an arbitrary $N$-way state space.

<Step id="data-model" title="Model the data">

- **oplog**: keyed by `(docId, rev)`, storing `{ opId, authorId, delta, ts }`. Partitioned by `docId` so loading the tail of operations since the last snapshot is a single contiguous partition range read.
- **snapshots**: keyed by `(docId, snapshotRev)` in object storage, holding compacted document state so opening an old document never replays 2 million historical keystrokes from `rev = 0`.
- **opdedup**: keyed by `(docId, opId)` with a 24h TTL so a client retrying after a dropped WebSocket connection does not apply its buffered insert twice.

<Step id="high-level" title="Draw the high-level architecture">

In the reference design:

1. Clients connect via **WebSocket gateways** (`gw1`, `gw2`) behind a **consistent-hash load balancer** so collaborators on `docId` route to the active **Document session service** (`collab`).
2. On `edit`, `collab` checks **Client opId dedup** (`opdedup`), appends the operation to the **Operation log store** (`opstore`), and publishes a compaction trigger to the **Snapshot compaction queue** (`compaction`).
3. **Snapshot compactors** (`compactor`) asynchronously fold tail operations into the **Document snapshots** object store (`snapstore`).
4. On `load`, `collab` checks the **Active document cache** (`doccache`) and on a miss loads the latest snapshot from `snapstore` plus tail operations from `opstore`.

<Step id="deep-dive" title="Deep dive: Operational Transformation vs Sequence CRDTs">

When Alice and Bob start from `"BCD"` (`rev 1`):
- Alice inserts `"A"` at index `0` $\rightarrow$ `"ABCD"`.
- Concurrently, Bob deletes index `1` (`"C"`) $\rightarrow$ `"BD"`.

If Alice's `"insert(0, 'A')"` is applied first on the server (`rev 2`), Bob's `"delete(1)"` arrives referencing `baseRev = 1`. Because Alice inserted a character **before** index `1`, `"C"` has shifted to index `2`!
- **Operational Transformation (OT)** shifts Bob's index (`1 + 1 = 2`) before applying it, producing `"ABD"` on all replicas.
- **Sequence CRDTs (RGA / Yjs / Automerge)** instead assign every character a globally unique, immutable ID `(clientId, lamportClock)` and specify insertions relative to the **ID of the left neighbour** (not a mutable integer index) and deletions as a tombstone on that ID. Because IDs never shift, operations commute in any order without a central server!

<Step id="alternatives" title="Evaluate alternatives">

- **No operation deduplication (`docs-no-dedup`)**: in the simulator, running the `lost-acks` scenario against the alternative without `opdedup` causes retried operations to append twice, triggering a `duplicateEffect` violation.
- **Full snapshot write on every edit (`docs-sync-snapshot`)**: writing the full snapshot to object storage synchronously on every edit slows down writes and drops goodput below 98%.
- **OT vs CRDT trade-off**: Google Docs uses server-ordered OT (small payloads, no tombstones, requires a central session server per doc); Figma and Yjs-based editors use CRDTs (natural offline/peer-to-peer merges, at the cost of tracking character IDs and periodically pruning tombstones).

<Step id="failures" title="Run the failure scenarios">

Run the three failure scenarios in the simulator:

- **Lost WebSocket acknowledgements (`lost-acks`)**: responses from `collab` to `gw1` drop for 80 ms after operations are already recorded in `opstore`. Gateway 1 retries with the same `opId`; `opdedup` suppresses duplicates (`clean: true`).
- **Compactor crash (`compactor-down`)**: `compactor` workers die for 700 ms. Live editing and loading continue at > 99% goodput because edits only need `opstore` and loads replay a slightly longer tail of operations until compactors catch up.
- **Company all-hands doc (`all-hands-doc`)**: 30% of traffic targets one hot document. `doccache` serves loads and the consistent-hashed session service serialises edits in memory.

<Step id="wrap-up" title="Wrap up and self-assess">

Review the four pillars of your design:
1. **Convergence engine**: single-server Jupiter OT (with single in-flight batch per client) or sequence CRDTs (RGA/Yjs).
2. **Idempotent WAL + checkpoints**: append small operations keyed by `(docId, opId)` to `oplog` and compact asynchronously into `snapshots`.
3. **Stateful session routing**: consistent-hash `docId` to one session owner with lease-based failover.
4. **Separate ephemeral plane**: keep cursors and presence in memory and cap active editors per document.
