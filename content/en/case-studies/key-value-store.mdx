<Step id="requirements" title="Requirements">

`put(key, value)`, `get(key)` and `delete(key)` for values up to ~1 MB (typically ~1 KB), optionally a conditional put on a version. Single-digit-millisecond p99 inside a region; writes accepted whenever a quorum is reachable; consistency tunable per request; scale to tens of TB and about a million operations a second by adding nodes.

<Step id="estimates" title="Estimates">

- **Data**: 10B keys × ~1 KB ≈ 10 TB, **30 TB** with N = 3.
- **Nodes for storage**: 30 TB ÷ ~2 TB usable each (room for compaction) ≈ **15**.
- **Nodes for throughput**: 1M ops/s with 70% reads at R = 2 and 30% writes sent to N = 3 replicas ≈ 2.3M replica operations/s ÷ ~100k per node ≈ **23**. Plan about 30 for headroom and node loss.
- **Joining a node**: consistent hashing moves about 1/31 of the data (about 1 TB), where hash mod N would move almost all of it.

<Step id="api" title="API">

- `GET /kv/{key}?consistency=quorum|one` → 200 with value and version, or 404.
- `PUT /kv/{key}` with an optional `If-Match: version` → 200 with the new version, or 409 on a version mismatch.
- `DELETE /kv/{key}` → writes a **tombstone**, garbage-collected after a grace period (10 days here) so a replica that was down cannot resurrect the value.

A plain put is an idempotent overwrite, so the coordinator can retry it safely after a timeout.

<Step id="data-model" title="Placing keys on a ring">

Each key hashes to a token on a ring. Its N = 3 replicas are the next three **distinct** nodes clockwise: the preference list. Each physical node owns many **virtual nodes** (64 here, 256 by default in Cassandra), so load spreads evenly and a failed node's keys spread across all survivors instead of one neighbour. Try it: add and remove nodes and watch how few keys move.

<Step id="high-level" title="High-level design">

Clients reach stateless **coordinators** through a load balancer. A coordinator hashes the key, sends the write to all N replicas and acknowledges after W of them reply; a read asks R replicas and returns the highest version. **Hinted handoff** writes to the next healthy node when an owner is down and hands the data back later; **read repair** fixes stale replicas a read touches.

<Step id="deep-dive" title="Deep dive: quorums">

If **R + W > N**, every read set overlaps the last write set in at least one replica, so a read sees the latest acknowledged write. N = 3, R = W = 2 tolerates one slow or dead replica on both paths; R = 1, W = 3 makes reads fast and writes fragile; **R = W = 1 is fastest but only eventually consistent**. Quorum overlap is not linearizability: concurrent writes still produce siblings that need versions (vector clocks in Dynamo, timestamps in Cassandra).

<Step id="alternatives" title="Alternatives">

- **Weak quorums, R = W = 1.** Lowest latency, but run the baseline against it: the engine reports stale reads — acknowledged writes invisible to later reads.
- **Leader per shard with Raft or Paxos** (etcd, TiKV, Spanner). Linearizable and conflict-free, but writes wait for a majority and stall during elections, and a minority partition cannot write.
- **Round-robin load balancing** in front of the coordinators. Ignores how busy each coordinator is, which matters in the partition scenario below.

<Step id="failures" title="Failure scenarios you can run">

- **5% packet loss** between a coordinator and the ring: lost requests time out after 30 ms and are retried with backoff. Put is an idempotent overwrite, so retries are safe and nearly every request succeeds; the tail gets fatter.
- **The ring slows 6×** (compaction or a noisy neighbour): p99 roughly quadruples but everything finishes inside the 200 ms deadline, because the ring has spare workers.
- **Coordinator 2 loses its path to the ring** but still passes health checks — a gray failure. The **least-connections** balancer rescues most requests: stuck requests keep coordinator 2's connection count high, so new requests go to coordinator 1. With round robin, half of all requests would keep falling into the hole.

<Step id="wrap-up" title="Wrap up">

Summarise: consistent-hash ring with virtual nodes, N = 3 and R = W = 2 by default with per-request overrides, hinted handoff and read repair for availability, Merkle-tree anti-entropy for keys nobody reads, tombstones with a grace period. Risks: compaction-induced latency, hot keys on one preference list, gray failures. Then score each stage from 1 to 4.
