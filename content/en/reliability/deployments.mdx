<Step id="strategies" title="Three ways to replace running code">

Most outages start with a change. The deployment strategy decides how many users see a bad change, and how fast you can take it back.

- **Rolling**: replace instances in batches. No extra capacity, but old and new versions serve side by side for the whole rollout, and rollback is another rolling deploy.
- **Blue/green**: bring up a complete new fleet (green) next to the old one (blue), test it, then switch traffic at the router. Rollback is switching back, in seconds, at the cost of running two fleets during the switch.
- **Canary**: send a small share of real traffic to the new version, compare its metrics with the old version, and widen in stages only if they match.

Strategies combine: a canary first, then a rolling or blue/green widening, with **bake time** at each stage. AWS's deployment pipelines go one zone in one region first, then widen across regions in waves.

<Step id="canary" title="A canary's blast radius">

A canary turns "will this break production?" into a bounded experiment. Its blast radius is the traffic share × the time until rollback × how badly it fails. Halving the canary share or the detection time halves the damage, which is why automated rollback on SLO metrics matters more than a careful human watching a dashboard.

A canary also needs enough traffic to be statistically meaningful: at 0.1% of a quiet service, it may take hours to see a single error.

<Step id="rolling" title="Rolling updates need headroom">

During a rolling update, the instances in the current batch are out of service: draining, restarting, warming caches. The rest carry all the traffic. Pick the batch so the remaining instances stay under your utilisation target at peak, not just under 100%, because a freshly restarted instance is slower until it warms up.

<Step id="config" title="Configuration is a deployment too">

On July 2, 2019, Cloudflare deployed a new web-application-firewall rule containing a regular expression that backtracked catastrophically. The rule went to every machine worldwide at once, CPU hit 100% everywhere, and traffic dropped for about 27 minutes. The code was fine; the **configuration** had skipped the staged rollout code would have had.

<Step id="flags" title="Separate deploy from release">

A **feature flag** ships new code dark and turns it on at runtime, for internal users, then 1%, then everyone. Turning the flag off is a rollback that takes seconds and needs no deploy. Flags carry costs: every flag doubles a code path to test, and stale flags pile up, so give each one an owner and a removal date.

A rollback is only safe if the old code can read what the new code wrote. Database changes therefore use **expand/contract**: add the new column or table first (both versions work), deploy code that writes both, migrate, switch reads, and only in a later release remove the old shape.

<Step id="rollback" title="Roll back first, debug later">

When a deploy correlates with a symptom, the fastest mitigation is usually to undo it. Debugging forward with a hotfix while users are failing spends error budget on your curiosity.
