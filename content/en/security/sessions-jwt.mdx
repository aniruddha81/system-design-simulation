<Step id="two-designs" title="A pointer or a passport">

After sign-in, the server must recognise the user on every later request. Two designs:

- **Server-side session**: the client holds an opaque, random session ID (OWASP asks for at least 64 bits of entropy) and the server looks it up in a session store on each request. Revocation is instant: delete the row. The cost is a store lookup per request, and a store that must be available.
- **Self-contained token**, usually a **JWT** (RFC 7519): the server signs a set of claims (`sub`, `exp`, `aud`, roles) and the client presents it. Any service with the verification key can check it with no lookup. The cost: the token stays valid until `exp` unless you build revocation, and it is larger than an ID on every request.

A JWT is **signed, not encrypted**: anyone holding it can base64url-decode the claims. Never put secrets in it.

<Step id="validate" title="Validating a JWT">

Most JWT vulnerabilities come from trusting the token's own header. RFC 8725 lists the classic attacks: accepting `"alg": "none"`, and **algorithm confusion**, where a server that expects RS256 is tricked into verifying an HS256 signature using its *public* key as the HMAC secret. The defence is to decide the algorithm and key on the server, never from the token.

<Step id="revocation" title="Revoking a token that verifies itself">

A self-contained token cannot be deleted. You can either wait out its lifetime, or keep a **denylist** of revoked token IDs (`jti`) that every service checks. A denylist only needs each entry until the token would have expired anyway, so its size is bounded: by Little's law, revocations per unit of time × token lifetime. Short lifetimes keep it small, and keep the lookup cheap enough to replicate everywhere.

Notice the irony: checking a denylist on every request is a lookup per request, which is the cost JWTs were meant to avoid. It is still a much smaller, read-mostly set than a full session store.

<Step id="lifetime" title="Short access tokens, rotating refresh tokens">

The standard compromise: **short-lived access tokens** (minutes) that APIs verify locally, plus a **long-lived refresh token** that only the authorisation server accepts and can revoke instantly. A stolen access token is useful only briefly; a stolen refresh token can be detected through **refresh token rotation**: each refresh returns a new refresh token and invalidates the old one, so a reused old token reveals theft and revokes the whole family, as the OAuth security best practice (RFC 9700) describes.

Shorter access lifetimes cost refresh traffic at the token endpoint.

<Step id="storage" title="Where the browser keeps it">

In a browser, any credential readable by JavaScript is readable by an XSS payload. A cookie with **HttpOnly** cannot be read by scripts; **Secure** sends it only over HTTPS; **SameSite=Lax** or **Strict** stops most cross-site requests from carrying it, which is the main defence against CSRF along with anti-CSRF tokens for state-changing requests. Regenerate the session ID at sign-in so a pre-set ID cannot be fixed on the victim.
