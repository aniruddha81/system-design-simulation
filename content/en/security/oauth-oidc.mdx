<Step id="roles" title="Delegation without the password">

A photo-printing site wants to read your photos from a storage service. Before OAuth, you would have given it your storage password, granting it everything, forever, until you changed the password. **OAuth 2.0** (RFC 6749) replaces that with a scoped, revocable token.

It names four roles: the **resource owner** (you), the **client** (the printing site), the **authorisation server** (which authenticates you and issues tokens), and the **resource server** (the photo API, which accepts tokens). The client never sees your password; it gets an access token limited to the scopes you approved, such as `photos.read`.

<Step id="flow" title="The authorisation code flow with PKCE">

The authorisation code flow sends the browser to the authorisation server, which returns a short-lived **code** through a redirect. The client then exchanges the code for tokens over a direct back-channel call. Tokens never pass through the browser's address bar.

**PKCE** (RFC 7636) adds a per-request secret. Before redirecting, the client generates a random `code_verifier` and sends only its hash, the `code_challenge` (S256 method). At the token endpoint, it must present the verifier itself. The `state` parameter, checked on return, ties the response to the request the client made.

<Step id="pkce" title="What PKCE protects">

On a phone, another app can register the same custom URL scheme and receive the redirect, including the code. Without PKCE, it could redeem that code. With PKCE, the code is useless without the verifier. RFC 9700 now recommends PKCE for every client, including server-side ones, because it also defeats code injection attacks.

The protection is only as strong as the verifier's randomness. RFC 7636 recommends 32 random bytes, base64url-encoded into 43 characters.

<Step id="grants" title="Choose the grant for the client">

Which flow fits depends on who the client is and whether it can keep a secret.

- **Browser apps and native apps**: authorisation code with PKCE. They are **public clients**: anything shipped to the user's device can be extracted.
- **Server-side web apps**: authorisation code with PKCE plus a client secret or private-key authentication.
- **Service-to-service with no user**: the **client credentials** grant.
- **Deprecated**: the **implicit** grant returned tokens in the URL fragment, where they leak through history and referrers; RFC 9700 says not to use it. The **resource owner password** grant hands the user's password to the client; RFC 9700 says it must not be used.

<Step id="oidc" title="OpenID Connect: who signed in">

OAuth tells a client what it may access. **OpenID Connect** adds who the user is. Request the `openid` scope and the token response also contains an **ID token**: a signed JWT whose `aud` is the client's own ID, with the user's `sub`, the issuer, the time of authentication and the `nonce` the client sent.

The two tokens have different audiences. The **ID token** is for the client, to establish a sign-in session. The **access token** is for the resource server. Sending an ID token to an API as if it were an access token is a common and dangerous mistake.
