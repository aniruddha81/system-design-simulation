<Step id="models" title="Silo, pool or bridge">

A **tenant** is a customer organisation sharing your system.

<Compare title="Tenancy models" sides={[
  { title: "Silo", tone: "ok", points: ["Own stack or database", "Easy delete and audit", "Costly at thousands"] },
  { title: "Pool", tone: "warn", points: ["Shared tables, tenant_id", "Cheapest", "Isolation is all in your code"] },
  { title: "Bridge", tone: "info", points: ["Mix of both", "Silo big or regulated tenants"] }
]} />

<Choice
  id="tenancy-model"
  objective="choose-isolation-model"
  prompt="You serve 20,000 small businesses and 15 large banks. The banks contractually require their data in separate databases with their own encryption keys. Which model fits?"
  options={[
    { id: "bridge", text: "Bridge: pool the small businesses, give each bank a siloed database with its own key", correct: true, feedback: "Right. You pay silo costs only where a contract requires it, and keep the long tail cheap to run." },
    { id: "silo-all", text: "Silo every tenant", feedback: "Isolation would be excellent, but 20,000 databases is a fleet to patch, migrate and monitor for customers who never asked for it." },
    { id: "pool-all", text: "Pool everyone, including the banks", feedback: "That breaks the banks' contractual requirement. A tenant_id column is not a separate database or key." },
    { id: "per-region", text: "One database per region", feedback: "Regions separate geography, not tenants. Banks would still share tables with everyone in their region." }
  ]}
/>

</Step>

<Step id="scoping" title="Scope every query to the tenant">

One missing `WHERE tenant_id = ?` leaks another customer's data. Take the tenant from the **authenticated context**, never a caller parameter, and add **defence in depth**: PostgreSQL row-level security filters every query.

<Flow title="Two layers of tenant scope" height={150} nodes={[
  { id: "t", label: "Token", kind: "apiGateway", x: 0, y: 50, note: "tenant = acme" },
  { id: "s", label: "Service", kind: "service", x: 50, y: 50, note: "WHERE tenant_id" },
  { id: "db", label: "RLS policy", kind: "database", x: 100, y: 50, note: "forces tenant filter" }
]} edges={[{ from: "t", to: "s" }, { from: "s", to: "db" }]} />

<Choice
  id="tenant-source"
  objective="enforce-tenant-scoping"
  prompt="An API endpoint receives tenant_id as a query parameter and uses it to filter results. What is wrong?"
  options={[
    { id: "trust", text: "The caller chooses the tenant. It must come from the authenticated identity, and be enforced again at the data layer", correct: true, feedback: "Right. Any caller can change a parameter. Derive the tenant from the verified token, and let row-level policies catch any query that forgets." },
    { id: "nothing", text: "Nothing, as long as the endpoint requires authentication", feedback: "Authentication tells you who the caller is. It does not stop a caller from asking for someone else's tenant." },
    { id: "encode", text: "The parameter should be base64-encoded", feedback: "Encoding is not access control. The attacker can encode a different tenant ID just as easily." },
    { id: "uuid", text: "Tenant IDs should be random UUIDs", feedback: "Unguessable IDs reduce enumeration, but IDs leak through invites, logs and support tickets. Check, do not hide." }
  ]}
/>

</Step>

<Step id="noisy" title="Noisy neighbours">

One tenant's spike or bulk import can slow everyone. Apply rate-limiting tools per tenant: quotas, per-tenant concurrency, fair queueing, separate pools for the consistently large.

<Compare title="Shared job queue" sides={[
  { title: "One FIFO", tone: "bad", points: ["Bulk import first", "Others wait hours"] },
  { title: "Fair per-tenant queues", tone: "ok", points: ["Bounded share each", "Import still runs"] }
]} />

<Choice
  id="noisy-fix"
  objective="limit-noisy-neighbours"
  prompt="One tenant's nightly bulk import fills the shared job queue, and every other tenant's jobs wait hours. Which change fixes this without new hardware?"
  options={[
    { id: "fair", text: "Per-tenant concurrency limits in the workers and fair scheduling across tenants' queues", correct: true, feedback: "Right. Each tenant gets a bounded share; the bulk import still runs, just without monopolising the workers." },
    { id: "fifo", text: "Keep one FIFO queue but make it larger", feedback: "A bigger FIFO holds more of the bulk import in front of everyone else. Waiting gets longer, not shorter." },
    { id: "priority", text: "Give the bulk-import tenant the highest priority so it finishes sooner", feedback: "That makes everyone else wait for it explicitly. The problem is the lack of fairness, not the import's speed." },
    { id: "ban", text: "Disable bulk imports", feedback: "It removes a feature customers pay for. Bounded per-tenant shares solve the same problem and keep the feature." }
  ]}
/>

</Step>

<Step id="shuffle" title="Shuffle sharding shrinks the blast radius">

Classic sharding: a bad tenant takes down its whole fixed group. **Shuffle sharding** (AWS Builders' Library) gives each tenant its own random set of k of n workers. A random other tenant shares your exact set with probability 1 ÷ (n choose k).

<Step id="cells" title="Cells: isolation for the whole stack">

**Cell-based architecture** isolates the whole stack: independent copies, each serving some tenants, behind a thin router. Deploy cell by cell; the first cell is your canary.

<Choice
  id="cell-benefit"
  objective="choose-isolation-model"
  prompt="You split a pooled service into 10 cells, each serving a tenth of the tenants. What do you gain?"
  options={[
    { id: "blast", text: "A failure or bad deploy in one cell affects about a tenth of tenants, and rollouts can proceed cell by cell", correct: true, feedback: "Right. Cells bound the blast radius and turn every deployment into a staged one." },
    { id: "cheaper", text: "The system becomes cheaper to run", feedback: "Usually the opposite: each cell carries its own overhead and headroom. You pay for isolation." },
    { id: "no-routing", text: "You no longer need a routing layer", feedback: "You now need one: something must map each tenant to its cell, and it must be highly available and simple." },
    { id: "no-big", text: "No tenant can ever outgrow a cell", feedback: "A large tenant can still outgrow one. Cells need a plan for moving or splitting tenants." }
  ]}
/>

</Step>
