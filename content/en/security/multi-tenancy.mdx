<Step id="models" title="Silo, pool or bridge">

A **tenant** is a customer organisation sharing your SaaS system with others. AWS's tenant isolation whitepaper names three models:

- **Silo**: each tenant gets its own stack or at least its own database. Strong isolation, simple per-tenant backup and deletion, easy to explain to auditors. Expensive per tenant, and thousands of silos are thousands of things to upgrade.
- **Pool**: all tenants share the same services and tables, separated by a `tenant_id`. Cheapest and simplest to operate. Isolation depends entirely on your code being right every time.
- **Bridge**: a mix, for example a pooled application tier with siloed databases, or pooled for the long tail and siloed for the largest or most regulated tenants.

<Step id="scoping" title="Scope every query to the tenant">

In a pooled model, one missing `WHERE tenant_id = ?` leaks another customer's data: the multi-tenant version of broken object level authorisation. Two rules keep this from happening. First, take the tenant from the **authenticated context** (the token or session), never from a request parameter the caller controls. Second, add **defence in depth** so a single bug is not enough: PostgreSQL's row-level security, for example, applies a policy to every query on a table, so a query that forgets the filter returns only the current tenant's rows.

<Step id="noisy" title="Noisy neighbours">

Shared capacity means one tenant's spike, runaway script or huge export can slow everyone. Isolation of **performance** matters as much as isolation of data. The tools are familiar from rate limiting, applied per tenant: quotas on requests and storage, per-tenant concurrency limits in workers, fair queueing so one tenant's backlog cannot starve others, and separate pools for tenants that are consistently large.

<Step id="shuffle" title="Shuffle sharding shrinks the blast radius">

Some failures are caused *by* a tenant: a poison request that crashes workers, or an attack aimed at one customer. With classic sharding, n workers split into fixed groups of k, and a bad tenant takes down its whole group, along with every other tenant in that group.

**Shuffle sharding**, described in AWS's Builders' Library, gives each tenant its own random set of k workers out of n. Two tenants rarely get the same set, so when one tenant's set fails, most other tenants still have at least one healthy worker. The number of distinct sets is n choose k, and a random other tenant shares your exact set with probability 1 ÷ (n choose k).

<Step id="cells" title="Cells: isolation for the whole stack">

Shuffle sharding isolates one tier. **Cell-based architecture** applies the same idea to the whole stack: each cell is a complete, independent copy of the service serving a subset of tenants, with a thin routing layer in front. A bad deploy, a poison tenant or a database failure affects one cell. Deploy cell by cell, and the first cell is your canary.
