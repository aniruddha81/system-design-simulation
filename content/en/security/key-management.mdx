<Step id="envelope" title="Envelope encryption">

Sending all data through a KMS does not scale (calls cap payload; AWS KMS takes 4 KB). **Envelope encryption**: encrypt data with a local **DEK**, **wrap** the DEK under a **KEK** that never leaves the KMS, store the wrapped DEK beside the ciphertext. Caching a DEK cuts KMS load but widens the blast radius.

  { from: "App", to: "KMS", label: "write: wrap my DEK under the KEK" },
  { from: "KMS", to: "App", label: "wrapped DEK", tone: "ok" },
  { from: "App", to: "KMS", label: "read: unwrap this DEK" },
  { from: "KMS", to: "App", label: "DEK (policy-checked, logged)", tone: "ok" }
]} caption="Data is encrypted locally with the DEK. Store the ciphertext with the wrapped DEK and drop the plaintext DEK." />

<Step id="hierarchy" title="Why the hierarchy helps">

The KEK is the one secret that matters. Data access becomes an audited, revocable *unwrap* permission.

<Step id="rotation" title="Rotation rewraps keys, not data">

Rotating a KEK makes a new **version**. Unwrap each DEK with the old version, rewrap with the new. Bulk data never moves: the job scales with the number of DEKs.

  { title: "Re-encrypt data", tone: "bad", points: ["Terabytes move", "Needed only if a DEK leaks"] }
]} />

<Step id="lifecycle" title="The key lifecycle">

NIST SP 800-57: every key is generated, activated, used for a **cryptoperiod**, deactivated, destroyed. One purpose per key. Plan compromise recovery in advance.

<Step id="secrets" title="Secrets are keys too">

Passwords, API keys and signing keys follow the same lifecycle. Never commit or bake them in. Fetch from a **secrets manager**, prefer short-lived credentials, rotate routinely.
