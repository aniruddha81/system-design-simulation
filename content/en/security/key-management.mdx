<Step id="envelope" title="Envelope encryption">

Encrypting terabytes directly with a key held in a **key management service** (KMS) or hardware security module would send every byte through it. KMS encrypt calls also cap the payload size; AWS KMS, for example, accepts at most 4 KB of plaintext per call. Instead, use **envelope encryption**:

1. Generate a **data encryption key** (DEK) locally or from the KMS, and encrypt the data with it.
2. Ask the KMS to encrypt (**wrap**) the DEK under a **key-encryption key** (KEK) that never leaves the KMS.
3. Store the wrapped DEK next to the ciphertext; discard the plaintext DEK.

To read, send the wrapped DEK to the KMS, get the DEK back, and decrypt locally. The KMS sees only small keys, enforces access policy on every unwrap, and logs each one. Caching a DEK across many objects trades a smaller KMS bill and load for a larger blast radius if one DEK leaks.

<Step id="hierarchy" title="Why the hierarchy helps">

The KEK is the one secret that matters, and it never leaves hardware you trust. Access to data becomes access to *unwrap*, which is an audited, revocable permission.

<Step id="rotation" title="Rotation rewraps keys, not data">

Rotating a KEK creates a new key **version**. New DEKs are wrapped with it; existing wrapped DEKs are decrypted with the old version and rewrapped with the new one. The old version stays available for decryption until nothing references it. The bulk data never moves, so the job scales with the number of DEKs, not with terabytes.

<Step id="lifecycle" title="The key lifecycle">

NIST SP 800-57 frames every key as having a lifecycle: generated, activated, used for a defined **cryptoperiod**, deactivated (decrypt or verify only), and eventually destroyed. Two rules from it prevent many incidents: use each key for **one purpose** only (never the same key for encryption and signing, or for two different systems), and plan **compromise recovery** before a compromise.

<Step id="secrets" title="Secrets are keys too">

Database passwords, API keys and signing keys are secrets with the same lifecycle. OWASP's guidance: never commit them to source control or bake them into images; fetch them at runtime from a **secrets manager** with per-workload access and audit logs; prefer **short-lived, automatically issued credentials** (workload identity, dynamic database users) over long-lived static ones; and rotate on a schedule so rotation is routine, not an emergency.
