<Step id="two-questions" title="Two different questions">

**Authentication** (authN) answers *who is making this request?* It verifies a credential: a password, a passkey, a signed token, a client certificate. **Authorisation** (authZ) answers *may this principal do this action on this resource?* It runs on every request, after authentication, and needs the resource in hand.

HTTP keeps them apart too: **401 Unauthorized** means "I do not know who you are, authenticate", and **403 Forbidden** means "I know who you are, and the answer is no".

<Step id="passwords" title="Store passwords for the day you are breached">

Assume the password table will leak one day, and make that day survivable. Never store the password, and never store a fast hash of it: a GPU computes billions of SHA-256 hashes per second. Use a **slow, memory-hard password hash** such as Argon2id, scrypt or bcrypt, as OWASP recommends, with a work factor tuned so one verification takes tens of milliseconds on your servers.

Add a unique random **salt** per user, stored next to the hash. Without salts, one pass of a dictionary cracks every user who chose a listed password at once, and identical passwords share a hash. With salts, the attacker pays for a separate pass per user.

<Step id="factors" title="Factors that resist phishing">

Passwords get phished, guessed and reused. A second factor helps, but not all factors are equal. A one-time code from SMS or an authenticator app can be typed into a convincing fake page and relayed to the real one within seconds. NIST SP 800-63B classifies SMS as a *restricted* authenticator, partly because of SIM-swap attacks.

**WebAuthn** credentials, including passkeys and hardware security keys, sign a challenge that includes the site's origin, so a signature made on a look-alike domain is useless on the real one.

<Step id="bola" title="Check the object, every time">

The top entry of the OWASP API Security Top 10 (2023) is **Broken Object Level Authorization** (BOLA, also called IDOR). The API authenticates the caller, then fetches `/invoices/8812` by the ID in the URL without checking that invoice 8812 belongs to them. Change the number, read someone else's invoice.

The fix is boring and must be universal: every handler that loads an object by an ID from the request checks the caller's permission on **that object**, on the server. Unguessable IDs make enumeration harder but are not authorisation.

<Step id="models" title="Roles, attributes or relationships">

Three common authorisation models:

- **RBAC**, role-based: users get roles, roles get permissions. Simple to audit; struggles when permissions depend on *which* object ("editor of *this* document").
- **ABAC**, attribute-based: a policy evaluates attributes of the user, the resource and the context ("same department, during business hours, from a managed device"). Expressive, harder to reason about and audit.
- **ReBAC**, relationship-based: permissions follow a graph of relationships ("user is a member of group G, which is an editor of folder F, which contains document D"). Google's Zanzibar paper describes this model serving sharing for products such as Drive and Calendar.

<Step id="layers" title="Where each check runs">

A request passes several checks, each where the needed information is available. The gateway can authenticate and apply coarse rules, but only the service that loads the object can decide object-level access.
