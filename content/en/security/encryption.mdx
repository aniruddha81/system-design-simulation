<Step id="in-transit" title="What TLS promises">

TLS 1.3 (RFC 8446) gives a connection three properties: **confidentiality** (an eavesdropper sees ciphertext), **integrity** (tampering is detected), and **server authentication** (the certificate proves the server holds a key for that name). Every TLS 1.3 key exchange is ephemeral, so recorded traffic stays safe even if the server's certificate key leaks later: **forward secrecy**.

TLS does not protect data once it arrives: the server, its logs and its database see plaintext. Nor does it stop a user from visiting `http://` first, where an attacker can strip the upgrade; **HSTS** (RFC 6797) tells the browser to use HTTPS only for that site.

<Step id="internal" title="Inside the network too">

"It is behind the firewall" assumes nobody is inside the network. Attackers who get one foothold, a misconfigured load balancer, or a cloud provider's shared fabric all break that assumption. Encrypt service-to-service traffic as well, and prefer **mutual TLS**, where both sides present certificates, so a service can authenticate its caller rather than trusting its IP address.

<Step id="handshakes" title="What handshakes cost">

A full TLS handshake costs the server a signature with its certificate's private key, and the client a round trip. **Session resumption** with a pre-shared key from an earlier connection skips the certificate signature, and connection reuse (HTTP keep-alive, HTTP/2 multiplexing) avoids handshakes entirely. On a busy edge, the resumption rate decides how much CPU goes to signatures.

<Step id="at-rest" title="Encryption at rest: which attacker?">

Encryption at rest comes in layers, and each one stops a different attacker:

- **Disk or volume encryption**: protects against a stolen or discarded disk. Anyone who can query the running database still sees plaintext.
- **Database-level encryption** (often called transparent data encryption): protects data files and backups if copied off the server. The database decrypts transparently for any authorised connection.
- **Application or field-level encryption**: the application encrypts specific fields (a national ID, a card number) with keys the database never sees. A SQL injection or a stolen database credential returns ciphertext.

The more selective the layer, the more it protects, and the more it costs: encrypted fields cannot be indexed or searched normally.

<Step id="nonce-limit" title="Keys wear out: the AES-GCM limit">

AES-GCM is an **authenticated** encryption mode: it encrypts and detects tampering in one step, and it needs a unique **nonce** (IV) for every message under a key. Reusing one nonce is catastrophic: it reveals the XOR of the two plaintexts and lets an attacker recover the authentication key and forge messages.

With random 96-bit IVs, collisions become likely long before 2^96 messages, so NIST SP 800-38D limits a key to **2^32 encryptions** with random IVs. A busy service reaches that faster than intuition suggests. Rotate keys by **usage**, not just by calendar, which envelope encryption makes cheap.
